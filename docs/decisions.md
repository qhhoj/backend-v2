# Design decisions

Decisions that still hold in the code, with the reason. Conventions and how-tos are in [CONTRIBUTING.md](../CONTRIBUTING.md).

## Program

- Big-bang cutover, old stack runs until the switch — one migration rehearsal path, no dual writes.
- MongoDB replica set with UUIDv7 `_id`s everywhere — transactions and change streams; UUIDv7 sorts by time, so lists sort by `-_id`.
- Django permission codenames kept as strings on users and groups — migrated data and checks keep their meaning.
- `/api/v2` (legacy read-only API) removed: no external consumer; the SPA uses the main API.
- Legacy integer-id URLs and API tokens are not carried over — handled later if needed.
- Dropped from the legacy site: IP auth, Lua label scripts, `atcoder` and `ecoo` contest formats, clarifications, the per-problem `shortCircuit` field — unused or a security/runtime cost.

## Foundation and auth

- Case-insensitive unique fields use collation `{locale: 'en', strength: 2}` — matches Django's behaviour.
- Pino through Fastify's own logger instead of `nestjs-pino` — fewer dependencies, same JSON output with request ids.
- `fastify` pinned to one copy — a duplicate copy breaks type identity with `@nestjs/platform-fastify`.
- `TRUST_PROXY` is `false` or an address list, never `true` or a hop count — per-IP rate limits would trust spoofed forwarded headers.
- Env is validated at boot — fail fast instead of a half-working process; a variable that became a setting only logs one warning (names, never values) and is ignored — an old `.env` must not stop a deploy or keep a stale value alive.
- `@nestjs/schedule` 6.x, `bullmq` 5.81.5, `@nestjs/bullmq` 11.0.5, `@fastify/cookie` 11.0.2, `sanitize-html` 2.17.5 pinned — newer majors are ESM-only and break Jest CJS and Nest 11 (`@nestjs/schedule` follows `^6.1.3`, the rest are exact).
- Passwords: verify Django `pbkdf2_sha256`/`pbkdf2_sha1` of any iteration count, rehash to 870000 on login — existing users log in with old passwords.
- Django's common-password list dropped; Have I Been Pwned range check instead — the HIBP list covers it; a pwned hit forces a password change.
- Login verifies the password before revealing a ban — the old site leaked ban state to anyone who knew a username.
- Login rate limit reserves a hit first and releases on success, per IP and per resolved account — only failures consume budget and concurrent guesses cannot race past the limit.
- Unknown usernames are limited per NFKC-lowercased name — avoids probing with case and Unicode variants.
- Wrong-password checks run a dummy PBKDF2 when the account is missing or the hash is malformed — no timing oracle for account existence.
- Sessions live in Redis keyed by `sha256(cookie)` with a per-user set — revoke-all is one lookup and a stolen Redis dump holds no usable cookies.
- Session cookie is `HttpOnly; SameSite=Lax`, state-changing requests carry `X-CSRF-Token`, and unsafe methods check `Origin` against `SITE_URL` — login has no session yet, so the `Origin` check is what protects it.
- API tokens (Bearer) skip CSRF, 2FA and pwned gates but cannot reach `@SessionOnly()` routes — a leaked token cannot change the password or mint a new token.
- The API token stays valid after a password change — documented choice; the holder cannot rotate credentials.
- An invalid Bearer token is 401 even on `@Public` routes — fail closed.
- TOTP and WebAuthn share one failure budget — a second factor cannot be brute-forced by alternating methods.
- TOTP rejects steps at or before `lastTotpTimecode` — a code cannot be replayed.
- TOTP secrets and scratch codes are AES-256-GCM encrypted at rest; the migrator decrypts the legacy Fernet format and re-seals it — a database leak does not leak second factors.
- 2FA enrolment and credential removal need `currentPassword` and are blocked while impersonating — a hijacked session cannot add its own second factor.
- Security keys are listed by `GET /auth/2fa/webauthn/credentials` (registration order, no credential id or public key), session-only and refused while impersonating; no rename route (not needed by the UI).
- Password change writes with optimistic concurrency (409) and rejects the same password — a race cannot overwrite a freshly changed password.
- Registration creates an inactive user plus a hashed activation key; `POST /auth/activate/resend` replaces the keys of a pending account and always answers 204 — a lost mail needs a way out, and resend adds no account-existence oracle (`POST /auth/register` still answers `email_taken`, limited to 5 per hour per IP).
- Password reset tokens are bound to the stored hash and `lastLogin` — single use without a token table; it also lets migrated social-only users set a first password.
- Social login state is bound to the browser by a cookie and the signup continuation by a second cookie — a stolen link cannot finish another browser's signup.
- Impersonation: active superusers only, never onto a superuser or nested, and the guard rechecks the impersonator on every request — rights loss ends the session at once.
- Session data goes through Redis cjson — no integers of 15+ digits, no arrays, `null` instead of `undefined`.
- `withRedisLock` is fail-fast (409 on contention) — a double click gets a conflict instead of queueing behind itself.
- ESLint `id-length` minimum 2 and one class per file named `<name>.<role>.ts` — readability rule for a team.
- Backup codes left come from `GET /auth/2fa/totp/scratch-codes` (`{ remaining }`), not a `/me` field — counting needs decryption, and a stored count could drift from the set.
- 429 from `RateLimitService.reserve` sends `Retry-After` from the longest TTL among the over-limit keys — clients can back off without guessing, and under-limit keys never extend the wait.
- A separate principal type, `ServiceClientPrincipal`, authenticates integration clients on `@ServiceOnly()` routes only (`qhi_` key, sha256 lookup, not revoked or expired, CIDR and scope checked on every request); the guard never builds `request.auth` for it, refuses sessions and user tokens there with 403 and keeps answering 401 for a `qhi_` value elsewhere (fail closed) — a client must never inherit user-route behaviour, and a user credential must never reach it.
- `IntegrationClient.expiresAt` (null = never): an expired key is refused like a revoked one in the same lookup, so a forgotten key stops working without an operator.
- A `@ServiceOnly()` route without `@RequireScope` refuses every key (default deny) — a new sync route cannot ship open by forgetting a decorator.
- Credential-minting routes (`/integration-clients`) are `@SessionOnly()` and `@NoImpersonation()`; new codenames reach migrated groups through the idempotent `grant-permissions` migrator command, run once after deploy — until then they are superuser-only.
- The `judge.manage_integration` anchor is `judge.change_miscconfig` (whoever edits site settings); verify at rehearsal that the migrated admin groups hold the new codename after `grant-permissions`.
- Failed `qhi_` lookups are counted per `request.ip`: 20 in 10 minutes, then 429 for every key from that address, valid ones included, until the window ends — the key is 256 bits, so this protects load, not secrecy; behind nginx `TRUST_PROXY` must list the proxy or all clients share one address and one sender of junk keys locks them all out (boot warning when active clients exist and it is off).
- Admin access follows rights, not the staff flag (amends fe:293): the session user carries `adminCapabilities.organizations` (admin of an organization, or `edit_all_organization`) because a permission list cannot tell it; `GET /problems?editable`, `GET /contests?editable` and `GET /organizations?administered` narrow the admin indexes to what the viewer may change. Every editor endpoint already checks the object (`editableProblem`, `editableContest`, `administered`), so non-staff authors and organization admins need no backend gate change.

## Migrator

- Backfill is incremental and re-runnable: stable `migrationIdMap`, upsert by `_id`, `--fresh` to empty — a full backfill runs ahead of time, delta catch-up and a short final run at the switch.
- `verify` rebuilds the expected document from source rows and deep-compares — counts alone miss field drift.
- Migrated stale-pending accounts are marked before the reclaim job can run: legacy admin-deactivated accounts migrate banned ("Account deactivated on the old site.", rank `banned`, unlisted, inactive) — user ruling; the stale-pending reclaim would otherwise delete them.
- Migrated submissions carry `casePoints`/`caseTotal` and the worker's `migration-recompute` follows the backfill — schema defaults make 0/0 rows look solved.
- Contest `formatConfig` keys are camelCased on migration, `cumtime` dropped on `final_submission`, `Ultimate` lowercased; Lua label scripts become `alpha` and are reported (6 contests, checked by hand) — the v2 schema rejects the legacy spellings.
- The id map covers only the jobs' `refTables` — log tables (13.3M activity, 3M sessions, 1.5M embedded cases, 443k reversion rows) need no ids; ~18.7M → ~0.4M entries.
- Submissions, comments, posts, tickets, messages, announcements and join requests get UUIDv7s stamped with the legacy creation time — `-_id` lists stay in time order.
- A mapper skips and reports a row it cannot import, and clears and reports a dangling reference; dependent jobs join on the same skip rules (`imported-rows.ts`) — one bad legacy row must not stop the run or leave a pointer to nothing.
- Derived values are recomputed by the worker's `migration-recompute` job, never by `contest-rescore` — a rescore would rewrite contest-submission points with the v2 rounding. `backfill` writes a migration marker, the job refuses to run without it, and `finish` clears it before go-live.
- Every rated contest is re-rated with the v2 rating code at migration, in end-time order (`migration-recompute` → `ContestRatingService.rateFrom`); legacy ratings are not kept — user ruling: one rating system from launch, so users' ratings may shift at launch.
- Badges (`judge_badge`, `judge_profile_badges`) are dropped, not migrated — user ruling; `verify` lists them as skipped by decision.
- Judges (`judge_judge*`) are not migrated: 17 names fail the v2 pattern and judge-v2 registers fresh at the big-bang cutover.
- Problem `points` outside 800..3500 are clamped and reported (19 on the real data) — user ruling.
- Test cases with status `RJ` are dropped and counted: v2 has no such case status and submission totals are unaffected.
- A row a v2 unique index refuses is reported by uuid and the run continues; a wrong `LEGACY_SECRET_KEY` aborts the users job — one duplicate must not stop 21M rows, and a wrong key must not turn 2FA off silently.
- An unknown legacy checker or grader leaves the problem's `data` null, never a fallback — a fallback would change verdicts on the next editor save.
- `init.yml` is copied, not regenerated, at migration — the judge contract is unchanged; the next data save regenerates it.
- `verify` also validates every mapped document against its v2 schema — a migrated row the API cannot save again is a migration bug.
- `check-files` (referenced problem data and media exist, never escaping their roots) and `check-integrity` (references, counts, rating coverage against the legacy source) are the post-recompute gates; the cutover runbook in `deploy/RUNBOOK.md` fixes their order.
- The migrator never loads `Env` — it reads `process.env` directly and a job fails with `<NAME> is required` (see the README env table).
- `migrator audit` runs read-only pre-import checks (zero dates, invalid JSON, case-only duplicates, unsupported hashes, WebAuthn rows); the id map is looked up per batch, never cached whole, and failed commands exit 1 — the legacy dump has 13M-row log tables and cutover scripts must see failures.

## Problems

- Statements render at save and the HTML is stored; reads never render — fast reads, one render budget per write.
- Render limits (markdown size, formulas, KaTeX output, tags, nesting, HTML size) are enforced and fail as 400 — a hostile statement cannot cost unbounded CPU.
- Markdown via `markdown-it` tuned to legacy `markdown2` output, KaTeX on the server, `sanitize-html` with the legacy allow-list; `problem-full` is unsanitized and needs `judge.problem_full_markup` — legacy parity with a permission around the unsafe path.
- Math spans are protected before Markdown and an unknown macro stays as raw TeX in `math-error` — a bad formula never fails a save.
- One rule set, `ProblemAccess`, for list and detail; the legacy quirk that admins do not see private problems in lists is dropped for a `visibility` filter — one source of truth.
- `visibleFilter` is only used in `find`/`count`, never in an aggregate — aggregate pipelines would need a different shape.
- Invisible or unknown problem is 404, visible but not editable is 403 — existence is not leaked.
- Catalog data (types, groups, licenses, languages, tags) is querier-backed and never deleted — small, hot, rarely changing.
- Uploaded file type is decided from the bytes; SVG is sanitized; nginx serves `/media` with `nosniff`, `attachment` for materials and a CSP sandbox — uploads cannot run script in the site origin.
- Test data stays on a shared volume, `PROBLEM_DATA_ROOT/<code>/`, as the judge contract; `init.yml` is generated from the embedded case list — the judges are unchanged, the DB is the source of truth.
- `init.yml` is written atomically (temp + rename); compile errors go to `data.feedback` and remove `init.yml` — a judge never reads a half-written or invalid config.
- A migrated problem saved unchanged must regenerate its legacy `init.yml` (checked against all 1372 migrated problems with cases on 2026-10-11, pinned by `problems-data.e2e-spec.ts`) — a save that drops or rewrites judging config would break a working problem.
- `<code>/.data-version` (the problem's `dataVersion`) is written last by every data writer (api data routes, Polygon import, seed); judges cache problem data by `(code, dataVersion)` and the bridge stores `judgedDataVersion`; existing directories are stamped once before the switch (`migrator stamp-data-versions`, cutover plan).
- Per-case bridged checkers are rejected (only the global custom checker is valid) — a legacy bug fixed.
- Zip uploads are bounded (entries, total size, per-entry size, ratio) and reject symlinks and path tricks — zip bombs and traversal.
- A code rename moves the data directory through the `codeRenamed` listener and drops cached PDFs; a rename during an import fails that import — the import's compare-and-set filters on `code`.
- Polygon import runs in the worker with pandoc under `prlimit --as=768MiB`, one job at a time, and reports through the job id — conversion cannot exhaust the box; a missing `prlimit` fails closed.
- Statement PDFs: Playwright job in the worker, cache `PDF_CACHE_ROOT/<code>.<lang>.pdf`, 202 while rendering, 503 with `Retry-After` on failure — render cost stays off the API.
- Tagging needs `allowTagging` plus `judge.add_tagproblem` or rating >= 1900; no external OJ calls — legacy rule, no outbound dependency.
- Languages admin has no delete and no key rename — judges report languages by key and submissions, problems and judges reference them; a rename or delete would orphan them.
- Soft delete is `deletedAt` (absent while live) filtered by `ProblemsRepository` in every finder; the deleted set is read by range so the sparse index serves it — one choke point, and a structural spec classifies every other direct reader of the collection so a new unfiltered read fails a test.
- Purge keeps submissions: it removes the data directory, rendered PDFs, packages, uploads (unless shared), comments and revisions and leaves a tombstone with code and name; `purgeStartedAt` is claimed first so a restore cannot interleave and a killed purge is simply rerun — students keep their history and re-rates stay stable.
- The purge deletes the problem's revisions; the structured `problem-purged` log line (problem id, code, counts) is the audit record — a tombstone has no statement left to diff against.
- A purge claims with `purgeStartedAt` (blocks restore) and sets `purgedAt` last; the sweep retries any claim an hour old, whatever the problem's age, so a crashed purge-now is finished the next night instead of waiting out the grace period.
- A symlinked problem data directory is refused by the purge (even one pointing inside the root): the judge marker would be written into the link's target and left there.
- A queued or running submission of a deleted problem is still judged (the bridge reads it deliberately unfiltered, with the problem's limits); effects ignore it, so points, solver counts and contest scores do not move.
- Submissions of a deleted or purged problem are visible only to their owner and to `judge.view_all_submission` holders, with no cases and no feedback; everyone else gets 404.
- Rejudge and reject of a submission of a deleted problem answer 409 `problem_deleted`: they would overwrite the history the purge ruling promises to keep (abort by the owner stays).
- Delete and restore recompute the solvers (points, solved counts) through their own `problem-solvers-recompute` job, because `problem-rescore` exits for a problem it cannot find; restore therefore brings the counters back.
- `deletedIds()` is read on every submissions list call, uncached: one `distinct` over a sparse index is cheap, and a cache would show a just-deleted problem's submissions to others until it expired.
- The package cache is an LRU keyed by the data version plus a hash of everything the package states (no statement revision exists), capped at 8 GiB with the oldest zips evicted first; packages live under `PDF_CACHE_ROOT/packages`, and the zip writer streams files (the text-only lazy zip cannot carry binary tests).
- Package requests spend the per-user budget (10 an hour) first and the per-problem one (3 an hour) second, and a refusal by either gives the other hit back — a refused request must not eat budget it did not use.
- Problem codes `deleted`, `meta` and `imports` are reserved (static routes and the imports prefix) by one `@IsProblemCode()` decorator on every DTO that names a new code; a deleted or tombstoned code stays taken forever by its row, and the Polygon create precheck says so before queueing.
- A contest save re-checks its problems after the write and puts every saved field back when one was deleted meanwhile (the rules revision stays raised: a number never names two texts; the ranking cache is purged), answering the same 400 as if the delete had come first; a save landing between the write and the revert is overwritten, last write wins as between two editors; with the delete's own re-check after `markDeleted`, whichever writes second sees the other — two compare-free writes on two collections leave no other way to close the race.
- Delete and restore emit `publicityChanged`: its listeners drop the public submission feed's cached eligibility at once, queue a rescore and move the suggester's contribution points; `problem-rescore` returns at once for a deleted problem (the solvers recompute moves its users), and after a restore it runs alongside the solvers job, which costs a second pass but changes nothing.
- Upload deletes (`StorageService.delete`, used by the purge) refuse a directory that resolves outside `MEDIA_ROOT` through a symlink, like data-directory deletes; the purge then fails and is retried nightly until an operator fixes the link, and a symlinked file itself is removed as a link — an rsync'd legacy media tree may hold such links, and a purge must never delete outside the root.
- The readers spec also catches the collection named by string (`collection('problems')`, `lookup('problems', ...)`, `each('problems', ...)`, `from:`/`foreign: 'problems'`) — the migration-only readers were invisible to it.
- Publishing after a contest skips a deleted problem with the reason `deleted` (the manual action loads it with `findIncludingDeleted` to say so; the worker's reader filters it and counts it as skipped).

## Judging and bridge

- Judges speak gRPC `qhhoj.judge.v1` (`judge-v2/proto`, vendored in `libs/judge-proto`): one bidirectional `Session` per judge plus `FetchSource`, TLS unless the bridge binds loopback (`JUDGE_BRIDGE_HOST` defaults to `127.0.0.1`; any other host needs `JUDGE_BRIDGE_TLS_CERT`/`_KEY`). The DMOJ protocol and the judge-server fork are gone in one switch, no mixed fleet — one typed contract for Rust and TypeScript, size caps and flow control from HTTP/2.
- The judge↔bridge contract is `judge-v2/proto` (`qhhoj.judge.v1`); backend-v2 vendors it at a judge-v2 tag into `libs/judge-proto` with `proto.lock.json` and the committed ts-proto output, and CI fails when either drifts — the Rust build needs the file at compile time, and the judge's releases are the versioned side.
- Inside v1 changes are additive only (new fields, oneof members, enum values; removed fields reserved), checked against `proto/compat/v1.shape.json`; `uint64` values stay ≤ 2^53 − 1 because the TypeScript side reads them as numbers.
- Conformance scenarios (`proto/conformance/scenarios`) are wire transcripts played by both repos: judge-v2 against its fake bridge and daemon, backend-v2 against the real bridge and Mongo; one matcher table pins both matchers.
- Mongo is the queue truth (`QU` plus `priority`); the bridge claims QU -> P before sending and the in-memory queue is rebuilt on start — a bridge restart loses nothing and never ends in IE.
- API -> bridge commands go over a Redis stream, fire-and-forget; a lost `judge` command waits for the bridge's resync — no RPC coupling, Mongo is the backstop.
- Every judge-driven write filters `{_id, judgedOn, judgeGeneration, judgeSeq: seq − 1, status}` and sets `judgeSeq: seq` in the same update; a claim `$inc`s `judgeGeneration`. A write that matched nothing is classified by one read (duplicate → re-ack, stale → ignore and abort the run, gap/order/full → protocol error) — at-least-once delivery with an exactly-once effect; a requeued or rejudged run can never write again.
- A message for a run the session does not hold (an older generation, an unknown id) is ignored and answered with one `Abort{ref}`; `Accepted` for a run the session never aborted is a protocol error and the session's own runs take the grace path — a judge that kept grading across a restart cannot poison the next run. A late `Accepted` for a run the bridge released (accept timeout) or voided (rejudge) is ignored. Such a run keeps its slot (`winding`) until the judge's `Final{ABORTED}` for it, which is neither stored nor acked: judge-v2 frees a slot only when the run's process returns, so the bridge never sends an `Assign` it would refuse with `SLOTS_FULL`.
- Credentials are gRPC metadata checked before any message is read; Hello first within 15 s (≤ 256 KiB), messages ≤ 4 MiB (grpc-js), 256 sockets and 8 per address without an authenticated session (a TCP server hands sockets to grpc-js through a connection injector to keep these caps) — unauthenticated memory and CPU stay bounded; the port is reachable only from judge hosts.
- Flood cap is 1000 messages/s per session counted on arrival, and the idle clock pauses while a message is handled; one message is handled at a time with the stream paused (HTTP/2 flow control then holds the judge back); only a pong to our own ping writes to Mongo.
- Case text is clipped by UTF-8 bytes (512, feedback 50) at a code-point boundary and cases are capped at 10000 — a submission document stays well under Mongo's 16 MB.
- File-only languages (B17) follow legacy: the upload is saved under `MEDIA_ROOT/submission_file/<code>/<userId>/<random>.<ext>`, the source is its media URL, `fileSizeLimit` is MB, and the judge fetches the file over `FetchSource`, served only for a run its live session holds, from `MEDIA_ROOT/submission_file/` (regular files only) — judges need no HTTP access to the site. Legacy rows hold `/submission_file/...`, which v2 does not serve: they judge once the migrator rewrites them to `${MEDIA_URL}/submission_file/...` and copies the files under `MEDIA_ROOT/submission_file/` (the migrator rewrites and `check-files` verifies them).
- Source length counts code points, not UTF-16 units — legacy Python `str` semantics; schema and DTO use one `codePointLength`.
- Judge key is compared in constant time against a sha256 hash; keys are shown once; block and rotate force-disconnect — a leaked or rotated key stops working immediately.
- Resync reconciles connected judges with Mongo (blocked, rotated key, disabled) and requeues P/G runs no session and no grace holds for two consecutive ticks; a bridge start resets nothing (judges are marked offline before any is served), so reconnecting judges resume their runs and the resync requeues the rest without spending `requeueCount`.
- A lost session's runs wait 30 s in grace; a judge that reconnects listing them in `Hello.inFlight` resumes from the next unstored seq without spending the requeue; on expiry the run is requeued once and IE the second time (AB if the api aborted it meanwhile); a rejudge restores the allowance. `Final{RETRY}` requeues without spending it and keeps that judge off the row until the next resync tick (this replaces the spec's 'banned for this dispatch round'); the third RETRY is IE (the spec's 'after 3 retries') — poison submissions cannot loop forever.
- Dispatch is per slot: the free slot with the lowest busy share, random tie-break; a rejudge never takes the last free slot while the capable judges have more than one; every judge sees the whole data root (no problem lists), so capability is the language; mirrors dispatch under `mirrorRoot`'s code and data version — rejudges cannot starve normal submissions.
- Priorities 0 contest, 1 normal, 2 rejudge, 3 batch rejudge, FIFO by id — UUIDv7 order is time order.
- Unfinished-submission limit is counted under a per-user Redis lock; `judge.spam_submission` bypasses — a burst of parallel submits cannot exceed the limit.
- Submission detail and source require the problem to be visible (404), owner included — a hidden problem's data does not leak through an old submission.
- Case output is shown unless `testcaseVisibility` is `O` (editors always) — default author-only problems must not leak outputs.
- Detail loads the thin row, checks access, then loads cases only when needed — avoids hydrating 10000 cases for a request that will be refused.
- Abort of a running submission is best-effort; the user aborts again — a lost `abort` would otherwise need a reliable channel. Known gaps: an abort published while the bridge is down (it reads commands from the newest entry at start, and a restart drops the grace marks), or while the run is being claimed, is not seen; the run is graded. Persisting an abort-requested flag would have to be cleared by every requeue path; not worth it for a restart window.
- An `Assign` not accepted within 20 s is aborted and released alone (QU, no requeue spent); the judge's other slots keep their work.
- `submission-graded` jobs from the bridge are named `<submissionId>.<generation>`: a Final resent before its ack (same session) re-enqueues the same id, which BullMQ drops while the first waits, and a rejudge is never taken for a duplicate. A Final resent after a bridge restart is dropped (the row is no longer P/G), so it cannot recover a lost job.
- Every write that finishes a submission (bridge D/CE/IE/AB, api abort of a queued row, reject) stamps `effectsDueAt`; the graded job clears the stamp it read once the effects are applied, and the 10-minute effects sweep re-applies every row due for more than 2 minutes (user, problem and contest results) — a bridge that dies between the write and the enqueue, or a Redis outage longer than ioredis' retries, delays a scoreboard by at most one sweep instead of losing the AC. A rejudge clears the stamp.
- GAS32 is not run by any judge — isolate 2.6's seccomp kills 32-bit binaries; legacy GAS32 submissions keep their stored verdicts and cannot be rejudged.
- One live session per judge name: a newer Hello replaces the older session, whose runs wait in grace for the newer to resume them — two streams can never both write one judge's runs.
- Rotating a key, blocking a judge and a forced disconnect revoke the live session at once — a leaked key stops working immediately, not at the next reconnect.
- Failed authentication is limited in memory to 20 per minute per address (not in Redis, not shared) — brute-forcing a key is slow without a new dependency, and one bridge is the only instance anyway.
- The TLS certificate is read at start; renewing it needs a bridge restart (judges reconnect and resume) — hot reload would add a watcher for a yearly event.
- The api refuses to rejudge a submission that is running (`P`/`G`) — voiding a live run is the abort path, and a rejudge racing a Final would need a second generation protocol.
- judge-v2 link constraints: `FetchSource` shares the session's connection (no second socket or credential), a judge retries after `PERMISSION_DENIED` (the run may not be assigned yet), and its reconnect backoff is 0.5–30 s — the bridge never has to chase judges.
- An api abort of a held run is remembered by the dispatcher, so it survives a dead stream: a resume sends `Abort` right after the Welcome and a grace expiry writes AB — a user's abort that reached a running bridge must not be graded (the restart gap above stays).
- A grace expiry whose Mongo write fails holds the run in grace again and retries at the next expiry — left to the resync, the stranded-run reset (free on purpose, for restarts) would requeue without spending `requeueCount`.
- A submit with `judgeId` stores the pin on the row (`pinnedJudge`): accept timeouts, resyncs, restarts and final judging keep it; a grace-expiry requeue or RETRY (the judge failed the run) and a rejudge clear it — an admin testing a judge must not see the run land elsewhere, and a run must not wait forever for a judge that cannot run it. A pinned row waits while its judge is offline; a rejudge frees it.
- v1.2 candidate "abort racing a disconnect" (not vendored; needs a hook holding loss handling): Hello{inFlight} → Welcome{CONTINUE} → Abort → Final ABORTED → ack, AB; with no reconnect the expiry writes AB.
- v1.2 candidate "rejudge during handshake" (not vendored; needs a hook holding the resume read): Welcome{CONTINUE} → Abort → Final ABORTED (winding, no ack) → Assign of the new generation; nothing precedes the Welcome.
- Bulk rejudge counts first (more than 10 needs `judge.rejudge_submission_lot`), then streams ids in chunks of at most 1000, skips locked rows without `force` — no full materialisation.
- The bridge is a single instance; the API and bridge refuse to boot while Redis is down (boot ping) — the orchestrator restarts them.
- judge-v2 reconnects by itself (backoff) and resumes its runs; systemd `Restart=always` only covers crashes.
- Bulk rejudge `dryRun` counts with the same filter and never throws for the lot limit (`allowed` tells the UI), so the confirm dialog can show the number first.
- Submission detail action flags come from the same pure rules the action endpoints enforce (`submissionActions`), so the UI cannot drift from the 403/409s.
- Bulk rejudge and rescore share one filter (2026-10-11): the scope is the contest (its editors, legacy `ContestAdmin.rejudge_view`), else the problem (its editors), else the site (`judge.edit_all_problem`), always plus `judge.rejudge_submission`; rescore queues the existing problem or contest rescore jobs instead of recomputing per row, and every real run is a `submission_batch` revision.
- Lock/unlock of one submission needs `judge.lock_submission` plus edit rights on the problem and is a `submission` revision; a judge is deleted only while offline (its pinned rows fall back at the next resync); the queue summary reads Mongo, the queue truth, never the bridge's memory.
- Submission `lockedAfter` is returned to editors only — the lock time is moderation information; an owner sees the lock as `canRejudge: false`.
- judge-v2 (Rust, repo `judge-v2`) replaces the DMOJ judge in one big-bang window with the site cutover; rollback is the old site with its DMOJ judges, never a mixed pair — one protocol on the bridge, one judge build in production.
- Judges read `PROBLEM_DATA_ROOT` over a read-only NFS mount (`actimeo=1`) and check `<code>/.data-version` (written last by the api; backfilled by `stamp-data-versions` after the final rsync) — no data transfer in the protocol; a lagging stamp is a RETRY, not a wrong grade.
- Bridge TLS uses a private CA pinned on judges, server name checked; the judge key stays a bearer secret in gRPC metadata — no mTLS in v1 (spec §1).
- Every isolate run starts from a fresh `--init` box — isolate 2.6 keeps the cgroup's peak memory and OOM flag across runs in one box, which would turn every case after an MLE into MLE.
- Languages no judge runs are removed from every problem before the switch (`prune-languages --keep <fleet list>`, cutover T3b) and their rows disabled, never deleted — a submission in them is refused at submit time instead of waiting in QU forever, and old submissions (GAS32 included) keep their language.
- Parity with DMOJ (cutover T5, `scripts/judge/parity`): any case or batch worth 0 points that fails skips every later case, also a 0-point sample in `test_cases` (DMOJ's documented rule, pinned by `par_zero_sample`); a full run grades `pretest_test_cases` first (a plain pretest worth 0, so the same rule applies; a pretest batch keeps its points), then `test_cases` — DMOJ's observed behaviour, pinned by `par_pre`. Accepted differences, judge-v2 kept: an uncaught exception is RTE, not DMOJ's IR (spec §8); memory over the limit is MLE from the cgroup, not DMOJ's RLIMIT_AS `bad_alloc` RTE; a testlib checker's message is the case feedback; testlib `quitp` partial points are a 0..1 fraction of the case.

## Effects and realtime

- Effects recompute from Mongo and `$set`, never increment; `runCoalesced` serialises one key across processes, extends its lock while running and reruns for marks left meanwhile — duplicate and retried jobs are harmless, bursts collapse.
- A sweep every 10 min recomputes users and problems with recently judged submissions, with a watermark set only after success (at most 24 h back) and a 10 min overlap — recovers lost `submission-graded` jobs.
- `submission-graded` is enqueued through `notifyGraded` with a 1 s bound, errors logged — a Redis outage must not block grading or the API; the sweep repairs the gap.
- Effects, sweep and rescore processors start only after the submission indexes exist (`startAfterIndexes`) — hinted queries throw before the index is built.
- User points: best per problem over public non-org-private problems, PP = sum of 0.98514^rank * points over the first 300 plus 0.05 per solved — legacy `calculate_points`; solved is AC with `casePoints >= caseTotal`.
- Problem stats exclude unlisted users; an AC counts only when `points >= problem.points` — legacy `update_stats`.
- Org PP and member counts are recomputed by the `organization-points` job (coalesced per organization), queued by membership changes and by user-points recomputes that move a member's PP — one writer, like user points.
- Rescore is queue-driven (`problem-rescore`), not an in-process event — the worker cannot reach the API's `ProblemEvents`; writes filter on the case totals read, so a rejudge that finished meanwhile keeps its points.
- Rescore uses `submissionPoints` (round after the ratio times points, as at grading end) — legacy rounded the ratio first; one rounding rule everywhere.
- `viewerStatus` is computed per page with one aggregate, not cached — no cache invalidation to get wrong.
- Events are Redis pub/sub carrying ids and status only, published by whoever writes the status, fire-and-forget and skipped while Redis is not ready — a Redis problem never fails a write; streams are never the source of truth.
- Status changes the bridge makes without a judge (start, resync) publish `queued` — open pages stay correct.
- SSE: the stream registers before reading state, rechecks access every 60 s, and sends `resync` after a lost subscription — no event gap between snapshot and live.
- SSE client limits: per user, per IP, total, feed and contest caps; slow clients are dropped on sustained backlog (2 s) or at once above 256 KiB; hijacked replies skip `onSend`, so streams never refresh the session cookie — memory stays bounded.
- Case events stream only when every case result is visible to the viewer; the public feed covers public non-org-private problems with no cases — no leak through progress events.
- Notification nudges ride a new per-user SSE channel, `GET /api/internal/events/user` (frame `notification {id}`), instead of a stream per feature — one stream per signed-in tab, with its own `userTotal` cap.
- Notification streams get their own cap: perUser 8 -> 12 (a tab holds a user stream plus up to three page streams), userTotal 2000, with feedTotal 1000 and contestTotal 1500 (was 2000) the capped channels sum to 4500 of `total` 5000, so submission and ticket streams always have a floor of 500 slots (a spec pins `total` minus the sum >= 500); perIp stays 16 (labs use `SSE_IP_ALLOWLIST`); limits stay per api process.
- Contest announcements write inbox rows through the `notification-fanout` job and send no SSE nudge — the contest stream already shows them; the bell catches up by polling.

## Contests

- Seven formats (`default`, `ioi`, `ioi16`, `icpc`, `vnoj`, `ultimate`, `final_submission`), one pure module each, validated config on every write — table-testable against legacy.
- `ultimate` writes `tiebreaker` (legacy wrote `tiebreak`), takes the latest row on equal dates (no double count) and honours `pointsPrecision` — legacy bugs fixed.
- No fifth ranking key `-submission_count`; ties fall back to participation id — deterministic order.
- `labelStyle` `numeric|alpha` replaces Lua label scripts — sandboxed Lua is a security and runtime cost.
- Contests embed at most `MAX_CONTEST_PROBLEMS` (100) unique problems — bounded document.
- Contest duration limit 14 days — legacy `VNOJ_CONTEST_DURATION_LIMIT`.
- Current contest is `users.currentParticipation`, validated lazily on read with compare-and-set — no per-request middleware.
- A current contest feeds `ProblemAccess`: before the start every problem is hidden, after it the contest's problems are visible whatever their own publicity; the editorial is 404 while in a contest — legacy parity.
- Contest submission list is filtered by contest, not by problem visibility or the viewer's scope — the legacy `ForceContestMixin` behaviour; access is still gated by contest rules.
- Access codes are hashed and compared in constant time; wrong guesses are rate limited per user and per IP, correct or missing codes cost nothing; editors skip the code — blocks guessing without punishing normal flow.
- A join after the registration window by an unregistered user is 409; `isRegistered` replaces the 1970 sentinel and is live-only.
- Attempt number counts within the participation — legacy semantics.
- A running final-submission (FSO) contest stores `PD` rows without sending them to the bridge; one delayed job `contest-final-judge` at `endTime` plus a 1-minute sweep requeues them at priority 3 — legacy's five trigger paths collapse into one.
- A single rejudge of a `PD` row is 409, bulk rejudge excludes `PD`, final judging skips rows already rejected, and leaving `final_submission` while `PD` rows exist is 409 — FSO judging owns those rows.
- The FSO queue-limit skip depends on the format, like legacy `in_fso_contest`.
- Contest effects ride the existing `submission-effects` job and recompute a participation through `runCoalesced` — one scoring path.
- Rescore (`contest-rescore`) runs on edits that change `scoringOf` (format, config, times, freeze, precision, problem id/points/partial/order) and on disqualification; other edits only purge the ranking keys — rescoring is expensive (about 34 s at 12k participations).
- Ranking is computed from participation fields and ordered `isDisqualified, -score, cumtime, tiebreaker`; the cache key is `{withVirtual, frozen}` with single-flight builds, every recompute purges all four keys — legacy left frozen keys stale; editors and own-row boards bypass the cache.
- Freeze applies to `icpc` and `vnoj` only, stays after the end (editors set `frozenLastMinutes` to 0 to unfreeze), and non-editors only ever see `frozen*` fields, in participations, which once leaked live standings.
- Hidden scoreboards list no scores to non-editors in participations — stricter than legacy, consistent with the freeze stance.
- Disqualify sets score -9999, bans the user from the contest, clears the current pointer, queues a rescore and re-rates when ratings exist; auto-ban after N disqualifications is off by default (setting `contest.banAfterDisqualifications`, 0 = off), lifts by compare-and-set on the ban reason, reconciled from the final `isDisqualified` — concurrent opposite requests converge and a manual ban is never lifted.
- Rating is Elo-MMR ported line for line (goldens generated from the legacy Python), queued by an editor or by the rescore of a contest that has ratings, one job at a time; it deletes and re-rates from the earliest affected end time in one Mongo transaction — a re-rate after any contest edit keeps later contests consistent.
- `contest-rescore` of a contest that has ratings enqueues `contest-rating` — the single trigger after disqualifications and scoring or end-time edits (broader than legacy); an end-time edit queues no rating itself, and the rating run's start moves earlier until it covers contests whose end moved.
- Rating is never computed from a frozen board: `POST /rate` answers 409 while the contest is frozen, the worker skips a target frozen at run time (logged) and leaves every contest still frozen at run time out of the re-rate chain (a contest is rateable once its board is unfrozen, like the `now` bound), and ratings follow live standings, which would reveal the hidden winner.
- A rated contest frozen again after rating loses its ratings on the next re-rate run covering its end; it is re-rated only by `POST /rate` after unfreezing — an automatic trigger cannot tell "never rated" from "deleted by a chain run" and would make manual rating automatic.
- Contest data download: zip written to a per-run temp name, sources fetched lazily, capped in bytes and entries, prepared at most once per 24 h unless the zip is missing; the root is outside `MEDIA_ROOT` — the zip is served by the API, never directly.
- Public ranking links use 18-char tokens with per-IP miss limits; both links and ranking codes serve the same `board` — frozen while frozen.
- Official ranking CSV is parsed at write with fixed size, row and column caps; the body limit is raised only on that route (and the problem data upload route).
- Announcements are rendered at save and pushed as ids over Redis `contest-events` and the shared SSE hub — one streaming stack for submissions and contests.
- Clarifications dropped (no rows in production).
- List rows carry the viewer's live status and current contest from one participation read per page (`$in` on the unique `{contest, user, virtual}` index) plus the pointer — no read per row.
- The detail shows the viewer's own cells frozen during a freeze, exactly as their ranking row — one freeze rule; attempts and pending flags read statuses only, never results.
- Solver counts are the ranking's `acceptedCount` rule from one aggregate over live rows, cached 30 s per frozen view and purged with the ranking keys, null unless the full board is visible — the detail must not rebuild the whole board per view or leak a hidden board.
- Register, join and leave refusals have one code each (legacy's distinct messages) with unchanged statuses — the SPA maps codes, never messages.
- No unregister — legacy has none (`ContestLeave` only clears the current contest); YAGNI.
- Announcements get no author and no server read state — neither the schema nor legacy has an author; ids are time-ordered, so the SPA keeps the last seen id.
- Contest settings echo `pushAnnouncements`, `hasRankingAccessCode`, per-problem output prefixes and a `users` lookup (ids stay, wire fields never change); `requiresRankingAccessCode` mirrors `requiresAccessCode`; the ranking code itself is never returned, only the boolean.
- Contest action status scans live queue jobs (no per-contest job id by design); there is no failed state because jobs are removed when they end.
- Sync clients own contests by `managedBy`, not by key prefix — a prefix lets a client rewrite a person's contest; on `PUT` any other existing key is one 403, and on `GET`, `DELETE`, participants and standings an unmanaged key is the same 404 as a missing one, so hidden and private keys cannot be probed. A synced contest is created hidden and private, authored by the client's acting user (`actsAs`), carries no organization, and freezes (409 `contest_frozen`) once a person publishes it or it starts, except for participants; standings serve the frozen board during a freeze.
- The acting user (`actsAs`) must hold `judge.add_contest` and `judge.create_private_contest`, is re-checked on every sync route (reads included) and may not be a superuser (refused at creation and per request); it may hold more permissions than the key's creator, since the creator only needs `judge.manage_integration` — granting a key is granting that user's contest powers, so pick a dedicated low-privilege account.
- `managedBy` is a binary UUID and the index is partial (`$type: 'binData'`, because Mongoose writes `null` on every contest): every query on it must state `$type: 'binData'` next to the equality or the planner skips the index.
- Sync `DELETE` is one conditional atomic delete (owned, hidden, not started) that then cascades what belongs to the contest alone (participations, announcements, public ranking link, ghosts); a contest that stopped qualifying meanwhile is 409 `contest_not_deletable` and keeps everything, and a contest with submissions is refused.
- The final-submission guard (leaving `final_submission` with unjudged pending rows is refused) lives in `applyFields`, shared by the editor and the sync `PUT` — one place instead of a check per caller.
- `SyncRateLimit`: one budget of 60 requests per minute per client across every sync route (429 beyond), charged before any work.
- Official contest mode is read only through `isOfficialModeActive` (flag plus lazy `contest.officialModeEndsAt`) — a site that forgot to switch it off unlocks itself; `GET /site` carries `officialMode` and may show a stale banner for up to its 60 s cache. New locks (organization order, join, leave, join requests) answer 403 `locked_in_official_contest`; the older five keep `forbidden`; tickets, administrator kicks and request decisions stay open; `usernameDisplayOverride` has no user-writable route (only the staff edit) so nothing locks it.
- Replay is a worker-built chunked stream of `[seconds, participantIndex, problemIndex, cell, score, cumtime, tiebreaker]` tuples from the real `scoreParticipation` on each submission prefix (5000 per chunk, 2 000 000 safety valve `replay_too_large`, old head stays) — a cap would break mid-contest order, and one format keeps the final state equal to the board.
- Replay times are seconds from each participation's own start — a windowed contest is meaningless on the contest clock.
- A build writes chunks under a new `buildId`, swaps the head, then deletes old chunks; chunk > 0 must send the `buildId` or gets 409 `replay_changed`, so a reader never mixes builds.
- No replay head is written or served before `endTime + 10 min` (`REPLAY_SETTLE_MS`) — the judge still works after the end; an earlier head is refused and rebuilt.
- Replay is gated by `boardReadable` plus ended, never `canSeeFullScoreboard` (403 `board_frozen` or `board_hidden`, then 409 `contest_not_ended`, then 409 `replay_unsupported`) — a freeze outlives the end and must not leak through replay.
- Replay builds start lazily on a read (202 `building`, at most one per contest per 30 s), after a ghost change, after a rescore, and from the editor button (ended contests, 3/hour).
- A failed enqueue of the editor's rebuild refunds its rate-limit budget — a Redis failure must not cost an attempt that queued nothing.
- A rescore queues a replay build delayed to end + settle — rescored scores change the stream, and an earlier build would be refused as unsettled.
- Ghosts are raw cells (minute, rejected tries up to 99, points) scored once in the worker through `scoreParticipation` into their own event stream; a ghost the format cannot rank is `unranked` and listed last — inventing data would mis-rank people.
- Ghost points are clamped to the problem's points at replay — a CSV written for other points must not outscore the problem.
- Ghost CSV import is all-or-nothing in one transaction; labels can be real names, so formula-looking labels and captions are refused and anonymised labels offered.
- Ghost CSV refusals carry one of 12 codes with a row: `label_missing`, `label_formula`, `label_repeats`, `label_invalid`, `caption_invalid`, `caption_formula`, `control_character`, `cell_invalid`, `columns_mismatch`, `header_invalid`, `csv_invalid`, `too_many_ghosts`; `*_invalid` on a label or caption means too long.
- The ghost body is capped at 1 MiB (`GHOST_CSV_MAX_BYTES`, Fastify answers 413) — a ghost set is a few thousand rows, and the body is parsed in memory.
- `final_submission` contests refuse only the ghost PUT (409 `ghost_unsupported_format`): scores exist only after the final judge, and listing, download and delete must still clean up what exists.
- Replay chunks of a build that died after `insertChunks` are orphans until the next good build (accepted); a contest delete path must remove the head, chunks and ghosts.
- Replay and ghost JSON is compressed by the nginx gzip location; the api registers no compression plugin.
- Balloons check order is `canSee` (404) then `canViewBalloons` (403) — a hidden contest stays invisible to someone who may not see it.
- Balloon refusals are coded `issues[]` under `conflict`, `not_found` or `forbidden` (`balloons_forbidden`, `contestant_forbidden`) — the SPA maps codes, never messages.
- `balloonStaff` is a per-contest user list, not a permission codename, and a clone clears it — volunteers are picked for one event, and a site-wide right would let them see every contest's queue.
- Balloons store only deliveries; the queue and first flag are derived from live cells on every read, so a GET writes nothing and a rescore leaves no stale flag. During a freeze volunteers still see live cells (runners must not stall), but contestants are refused, non-editors read `solvedAt: null`, and frozen reads are audited.
- Feed keys are stored hashed (sha256), compared in constant time, and only the newest key of a contest is accepted — minting revokes the rest, so a leaked old key dies with the next mint.
- Minting, revoking and releasing a feed key need an editor's own session (`@SessionOnly`, `@NoImpersonation`) — a credential that outlives the session must not come from a token or an impersonation.
- A feed key's default mode is `frozen-until-release`, and a release counts only for the freeze current when it was made — a resolver gets the frozen results only when an editor says so, and an old release cannot open a later freeze.
- Every feed refusal is the same 401 with a Basic challenge, and failed attempts spend one per-IP budget (5 per 10 minutes) taken before the contest is looked up: a locked IP gets the same 429 for every contest key — per-contest buckets answered 429 for made-up keys but 401 for real ones, which let a prober find hidden contest keys. The cost: clients behind one NAT address share the budget, so a resolver retrying a revoked key locks every feed from that address for 10 minutes.
- The feed refuses contests over 100 000 submissions (`feed_too_large`) instead of truncating, and leaves out a submission whose problem, language or team the feed does not list — a resolver must never see a dangling id.
- The feed snapshot is NDJSON, not JSON: resolver tools read lines; `schema-quality` exempts it from the event-stream rule through `NDJSON_SNAPSHOTS`.
- The live feed stream sits under `/events/` with the other streams, one shared room per contest (one build per tick for all its streams), caps of 100 feed streams in total (`contestFeedTotal`, its own cap; the public submission feed went 1000 -> 900 so the capped channels still sum to 4500 of 5000) and 2 per key — N resolvers must cost one build, not N, and the reserve for submission and ticket streams must hold.
- The feed stream is documented as `application/x-ndjson` with one line schema (`@ApiNdjsonStream`), not as SSE frames — it is what the wire carries, and an SDK client parsing SSE would see no event.
- A shared build error retries on the next tick and ends the streams only after repeated failures; the room cache key includes the freeze config (format, freeze minutes, end time), so an editor's freeze change is served at once — one failed read must not drop every resolver.
- The submissions export is editors-only, once a day, and includes the sources — sources are private data, and a zip of a large contest is expensive.
- The export's CSV prefixes a cell starting with `=`, `+`, `-`, `@`, tab or CR with `'` — usernames are user-chosen and a spreadsheet would run them as formulas.
- The export keeps the CSV rows of a problem deleted since the contest (including one taken out of the contest first, which the delete requires) but leaves out their sources — B4 shows a deleted problem's sources only to their owner and `view_all_submission` holders, and the zip is built once for any editor to download; the rows stay because contest-scoped lists still show them (M11).
- The export download is `private, no-store` like the package — the zip holds every contestant's source.
- `thawed` is null until a real release — a key that was never released has not thawed anything.
- A verdict graded after a contest's end on a live, qualified participation queues a coalesced replay rebuild from the effects job — a judge backlog past end + settle would otherwise leave the replay's final frame behind the board forever; virtual and spectating rows never queue (they submit to ended contests indefinitely).
- A replay request that finds the contest's build delayed past its own time removes it and adds one at the new delay (never `changeDelay`, whose delay is relative to the call, so `timestamp + delay` stays the true due time) — a build queued for the old end must not hold back a contest ended early; the editor's rebuild budget is given back when a not-yet-started build already covers the request.
- Replay build ids are UUIDv7 taken before a build reads anything; the head is swapped only to a later-started build, and a build deletes only chunks of builds that started before it — a run re-started after its lock lapsed can never delete or overtake a newer build still being written.
- The ghost list and the replay compute ranked/unranked over the contest's current problems only (`currentGhostGap`) — a removed problem's cell must not unrank a ghost in one view and not the other.
- The ghost CSV download starts with a UTF-8 BOM — Excel shows Vietnamese labels as mojibake without it; the import already strips it.
- A hidden board is 403 `forbidden` with issue `board_hidden` on both the replay and the sync standings — one wire shape, so clients match the issue code.
- Replay Redis failures are coded: the lazy read answers 404 `replay_not_ready`, the editor's rebuild 503 `replay_unavailable` (budget refunded), never a bare 500.
- Contest tag cap is count-then-insert, so a race can exceed 100; the cost is a few extra tags, a lock would add a dependency for no real harm.
- The contest tag catalogue is cached per API instance (`ContestTagsQuerier`), so a new tag can be unknown on another instance until its resync.
- Contest rules acceptance is enforced where a participation is created: register, first live join and every virtual join; a repeat live join keeps the stored acceptance.
- `rulesRevision` is compare-and-set, so a concurrent save of the rules gets 409 instead of a lost update.
- New issue codes `rules_not_accepted` (field `acceptRules`) and `unknown_tag` (field `tags`, one issue per slug).
- Manual publish (`publish-problems`) costs 5 per hour per user; dry runs are free and only completed runs count (a failed run is refunded).
- The editorial release is compare-and-set on the stored solution, so racing runs write one revision.
- The publish worker re-checks the recorded editor at job time (account active, rights now, group rights included), because rights may be revoked between switch and end; it skips deleted problems.
- Cloning a contest resets `publishAfterEnd`, `publishAfterEndBy` and `autoPublishOutcome`: the clone is a new contest and must not publish on a copied switch.
- Contest tags are a managed catalogue (querier-backed, colour = theme token key) and can be deleted, an exception to the never-deleted catalogue rule: contests keep the slug and show a neutral chip, because a tag is a label, not an identity others reference.
- One `publishVerdict` decides manual publish, its dry run and the automatic job; `ProblemAccess` moved to `libs/problems` so the worker applies the same edit rules — the paths cannot disagree. Rights are judged before flags (an actor without rights sees `no_permission`, never `organization_private`) and a trashed problem is `deleted`, not `not_found`.
- The automatic publish bypasses `ProblemEvents`: the worker enqueues the rescore and contribution-points jobs itself, so the feed's publicity cache (`submission-streams.service.ts`) is dropped only by its TTL; accepted.
- The automatic publish flips `isPublic` and writes its revision in one transaction; a problem found public with that contest's revision means a crashed run, so its follow-up jobs are queued again (both idempotent) and it is counted as published.
- The worker also re-checks that the recorded editor still edits the contest (`judge.edit_all_contest`, or `judge.edit_own_contest` as author or curator), failing with `cannot_edit_contest`, as the manual route requires.
- The minute publish sweep reads a partial index (`publish_after_end_due`, only contests with the switch on), so it does not scan the archive of past contests.
- Contest problem limits follow `ProblemAccess.canSee` (with the contest scope for a viewer inside the contest), so the overview never shows a limit the problem page would 404.
- New permission codenames are granted by the idempotent `grant-permissions` migrator command, keyed on an anchor permission (held by groups or users directly), not on group names; `verify` ignores the granted codenames, so it may run before or after the command.
- Contest admin ops (2026-10-11): per-problem rejudge reuses the bulk-rejudge rules scoped to `{contest, problem}` and needs edit rights on the contest plus `judge.rejudge_submission` (not problem edit rights, which a contest editor may lack); per-problem rescore and per-participation recompute are the contest rescore job narrowed by `problemId` or `participationId` (re-rate and replay follow-ups unchanged).
- Contest delete: editors only, key typed again; only hidden, unrated contests with no queued, judging or pending submissions (a rated one shifted later ratings). The row goes first (conditional on still hidden), then a `contest` delete revision, then every contest-keyed collection (participations, contest submissions, announcements, ranking link, ghosts, balloons, feed keys, replay head and chunks, official ranking, similarity runs and pairs) and current pointers; a failing cascade leaves orphans the revision names. Submissions are kept with `contest: null` (legacy `SET_NULL`); the org quota charge is not refunded; a participation delete racing a first submission is accepted (editors delete stray rows).
- Hand-edited participations: add live (one per user) or virtual, move `realStart` (ends a pending registration, queues a recompute), delete only rows without submissions (disqualify otherwise); the user's current contest is never set by an editor. Each write is a `contestParticipation` revision.
- Announcement edit keeps `createdAt` and is not pushed again (resend does that); the composer preview renders through the same `problem` profile as posting, for contest editors.

## Organizations and users

- Membership stays `users.organizations` (ordered array, no membership collection) — legacy has no role or join date; the principal already carries it.
- Migrated `about` (users and organizations) is rendered into `aboutHtml` on backfill, and `organizations.memberCount`/`performancePoints` are recomputed by `migration-recompute` — reads never render and the job writes the counts.
- Unlisted organizations are kept out of every enumeration but stay reachable by slug — legacy leaked them through select2 and the sitemap; a private unlisted organization is joined through its link.
- Joins and profile reorders are compare-and-set on the membership array; approvals run under a per-organization Redis lock against a live member count — parallel requests cannot pass the open-organization cap or `slots`.
- A personal look (accent preset, glass, glow) is one nullable `appearance` object on the user, replaced whole by PATCH /profile and cleared by null — the SPA sends the whole look, null means "use the site's"; the colour mode stays in `siteTheme`.
- Accent presets are a closed enum (`APPEARANCE_ACCENTS`), not free colours — the SPA checks contrast per preset, a free colour cannot be checked.
- Profile edit can only reorder or leave organizations — legacy let users self-join private organizations through the profile form.
- `edit_all_organization` decides join requests and `spam_organization` lifts the admin cap — legacy ignored the first and its permission typo made the second superuser-only.
- `about` renders in a `user` style that escapes raw HTML — legacy `safe_mode = 'escape'`.
- PATCH bodies refuse `null` outside a per-DTO allowlist (`RefuseNullFieldsPipe`) — `null` used to be stored or crash.
- Org-points enqueues coalesce through a Redis NX pending flag per organization — a burst of joins costs one recompute.
- A failed org-points enqueue is logged and lost until the next membership or PP change — a Redis outage must not fail the write, like `submission-graded` but without a sweep.
- Hinted organization member and submission reads need their indexes built before serving — `.hint()` throws on a missing index, so deploy runs `autoIndex` or `syncIndexes` first; leaderboards rely on the index the planner picks, with no `.hint()`.
- Leaderboard ranks follow the sorted field and continue across pages — legacy keyed every board on PP and restarted at the page offset.
- `GET /users?sort=contributionPoints` reuses the existing `{isUnlisted, isActive, contributionPoints, _id}` leaderboard index and the rank rules of the other sorts; `/contributors` stays as the same board.
- PP breakdown is its own paged route (the spec had one `/solved`) — it is cached per user for 600 s, so a problem that just turned private can show up to 600 s.
- The heatmap uses the viewer's zone like legacy; the spec's "user's timezone" reads as the viewer — and buckets days with Mongo's time-zone support, where legacy used `utcoffset().seconds`, wrong for negative offsets.
- Muted users may edit profile settings except `about` — muting silences public text, not account settings.
- `firstName` is editable (<= 30) and blocked in official-contest mode — legacy parity with `about`.
- A ban cannot use the automatic cheating reason — that reason is reserved for automatic contest-cheating bans.
- Join requests are limited (5 per hour per user) — legacy had no limit.
- User data zips live 7 days outside `MEDIA_ROOT` (and apart from `CONTEST_DATA_ROOT`), at most 3 prepares per user per day, served by the api — legacy kept them forever in a cache directory.
- New organization admins join the `Org Admin` group on update as well as create — legacy granted it on create only; it is never revoked, like legacy.
- One rule, `ContestAccess.boardReadable`, decides whether a viewer may read results derived from a board; the user's ratings page uses it. An unreadable board keeps its history entry with null rank, performance and rating, and the rating summary (min, max, count) counts readable entries only.
- Organization summaries carry `isOpen`; home users carry the first listed organization through `OrganizationsService.firstListedByUser`, shared with the leaderboard — one rule, so the two lists cannot disagree.
- Staff user list uses a CI-collated username range (an `i` regex cannot use the index) and a partial `banReason` index; ban duration is deferred because it needs an expiry sweep.
- A searched staff user list is ordered by username along the same CI index (no in-memory sort), `page` is capped at 500 to bound the skip cost, and `banned=false` means not banned (no `banReason`).
- Short links lead only to same-site canonical paths (`/problems/:code`, `/contests/:key[/tab]`, `/blog/:id`, `/users/:name`, `/organizations/:slug`; no query, fragment, scheme or host), checked at creation and again at every redirect, which sends a relative `Location` — an open redirect would turn the site into a phishing relay; anyone signed in gets the idempotent automatic link of a path (20 new a day), only `judge.manage_short_link` holders choose codes or expiries, list everything or delete.
- Organization problem tags and the archived flag live in link collections (`organizationProblemTags`, `organizationProblems`), not on problem documents — org admins never write problems, two organizations cannot overwrite each other, a purge needs no cleanup; archived problems stay visible and submittable (archiving is housekeeping, not hiding), and the problem page learns of it through `GET /problems/:code/archived-in`.
- Contest tags and organization problem tags share one `TagColor` enum (`TAG_COLORS`, one OpenAPI schema) — the palette is identical, so one constant and one frontend component.
- Quota credits are an atomic three-step spend (reject above-limit prices up front, upsert-only `$setOnInsert`, guarded `$inc` without upsert) with a refund ledger row when the write fails — the first spend is limited, and an over-limit month answers `quota_exceeded`, never a duplicate-key 500.
- Quota rolls out warn-only: `quota.enforce` defaults to `warn` and `enforce` is honoured only after the `dataBytes` backfill set `quota:databytes-backfilled` — a half-measured site must not block organizations; deploy the api before the worker so the backfill does not race the writes.
- Quota charges the first listed organization of an organization-private problem or contest (create and clone); superusers and subjects with no organization are exempt; source-file uploads and Polygon imports cost no credits (small files; an enqueued job cannot be refunded) but are storage-metered.
- A contest edit that makes a contest organization-scoped charges the first organization once, refunded if the save fails; a contest already scoped is never re-charged — otherwise flipping a public contest to private skipped the quota. A problem edit that adds an organization is not charged (accepted gap).
- Staff with `judge.manage_short_link` are exempt from the 20-a-day short-link quota — they create links for the site, not for themselves.
- Storage used is the sum of `dataBytes` of organization-private problems by first organization, deleted-but-not-purged included — deleting and re-uploading cannot bypass the cap during the grace period.
- The `dataBytes` backfill writes with a compare-and-set against the value it read and does not take the data lock — a read of the directory must not stall the judge, and a data write that recomputed `dataBytes` meanwhile is fresher and wins.
- The storage cap is a soft meter checked outside the data lock — two parallel uploads to different problems of one organization can both pass and overshoot once; `dataBytes` is re-measured on every write, so the next check sees the true total.
- A failed `setDataBytes` after a data write is logged, not thrown, and credits are not refunded — the files and the version stamp are already in place; `dataBytes` stays stale until the next write or the one-off `problem-databytes` backfill (the nightly audit only logs drift).
- The nightly `organization-usage-audit` only logs drift between the credit counter and the ledger — it never rewrites the counter, so a person decides which side is right.
- The quota month key comes from `site.timeZone`, not a hard-coded zone (month boundaries follow the setting) — the key rolls over by itself and needs no reset job.
- The 80% near-limit threshold is QHHOJ's own choice (a common default), shown on the dashboard and sent once per organization, meter and month as a `quota-warning` notification (claim first with an atomic `$addToSet` on `warnedMeters`, then send; a failed send is logged and not retried); the backfill flag lives in Redis only, so the api logs a warning at boot when `enforce` is set but the flag is missing (a flushed Redis silently returns to `warn`), and a backfill that failed three times stays failed under its fixed job id: remove job `problem-databytes-backfill-v1` and restart the worker to re-run it.
- Credits of an archive upload are refunded when the data store or the final rename of the staged file fails; a failure after that (revision record) keeps the charge — the data is stored by then.
- Organization slug `usage` is reserved — `GET /organizations/usage` is a static route and wins over `:slug`.
- `OrganizationProblemResponse.updatedAt` is the problem document's own `updatedAt` (Mongoose timestamps), so counter writes move it too — the list shows "last touched", not "last edited by a person".
- `recent[].actor` on the usage dashboard comes from the ledger's `user`; null for a system entry (no user) or a deleted user.
- Organization delete is a superuser-only soft delete (`deletedAt`; every `OrganizationsRepository` read skips it, the slug stays reserved): problems and contests are unlinked and keep their privacy flags, so an organization-private one left with no organization is visible only to its editors; posts are unlinked and hidden (a post without an organization is public once visible); members are released, pending requests rejected, the organization's problem links and tags removed; `Org Admin` is not revoked, like any admin removal. It is marked first so no join or admin action reaches it while it is detached; the unlinks are idempotent and a repeated delete on the slug runs them again; there is no restore.
- Organization submissions (`GET /organizations/:slug/submissions`) list the listed members' submissions (task spec; unlisted users stay out as in the member list; legacy `SubmissionListOrganization` listed submissions on the organization's problems instead), through the site list's own filter so problem visibility, deleted-problem history and closed contest lists apply unchanged; readable by members, administrators and `judge.view_all_submission` (legacy `permission_bypass`). The stats strip stays site-wide: per-organization counts would depend on the viewer and could not share the cache.
- Organization create (2026-10-11, teacher feedback): `POST /organizations/:slug/problems|contests` follow legacy `ProblemCreateOrganization` / `ContestCreateOrganization` (behaviour from the old qhhoj/online-judge site): an administrator (or `edit_all_organization`) holding `create_organization_problem` / `create_private_contest`, which the `Org Admin` role carries; no `add_problem` / `add_contest`. The server sets `organizations` to that one organization and `isOrganizationPrivate`, so client values are ignored and those fields open no staff gate; every other gate, the creator-as-curator/author rule and the quota charge are unchanged. Editing stays `canEdit` (`edit_own_*` plus editor) — no organization leg, so the API and worker keep one rule. One rule (`OrganizationAccess.canCreate*`) feeds the routes, the organization `viewer` flags and the session `problemCreation` / `contestCreation` scopes; the SPA derives nothing.
- Organization problem codes start with the slug's lowercase letters and digits and `_` (`thpt-demo` → `thptdemo_`; legacy form rule, the slug and not `shortName`; the match rate against migrated codes was not measured — no local migrated copy, org-private problems are not public). A long slug keeps its first 23 letters and digits, so 8 characters stay free under the 32-character code limit. Checked on an organization create and on an edit of an organization-private problem that changes the code or the organization list (first live listed organization, like quota; a site problem merely listed under an organization keeps its code); existing codes are never re-checked; superusers are exempt; 400 issue `organization_code_prefix`, worded by the SPA. Contest keys get no prefix rule.
- On an organization-private problem `isPublic` only reaches members, so an editor who may create organization problems in every one of its organizations may set it without `change_public_visibility` (legacy organization form showed the field).

## Blog and comments

- Comment pages store the entity id with a type (`problem`, `editorial`, `contest`, `blog`, `tagProblem`); the API takes natural keys — a problem rename never orphans a thread.
- One `CommentPagesService` decides page access by reusing `ProblemAccess` (with the contest scope), the editorial rule, `ContestAccess` and `BlogAccess` — comments, votes, recent comments, feeds and the user tab cannot drift from the pages they belong to.
- A problem of the viewer's started contest shows no thread and takes no comment, like legacy's clarifications area; a plain `commentLocks` lock keeps the thread readable — an open thread would leak hints during the contest.
- Threads: roots newest first, replies in `path` order, depth <= 100, all replies of a page of roots loaded — legacy MPTT put siblings newest first and had no cap; the 10-comments-per-5-minutes limit bounds growth.
- Subtree hide and unhide filter with an `$or` of equality and a prefix regex — a single `^path(/|$)` regex has no index bounds and scans the whole `path` index.
- Comment-thread reads `.hint()` `{threadId, hidden, path}` — the indexes must be built before serving.
- Comments record `hiddenBy` (the comment whose hide hid them, itself for a direct hide); unhide clears only the rows that comment hid, so a reply hidden on its own stays hidden when an ancestor is unhidden. Legacy hidden comments migrate with `hiddenBy` = own id.
- Unhiding under a hidden parent is 409 — otherwise a visible orphan shows in lists, counts and points.
- Votes are changeable and withdrawable; the vote row and the target's score change in one transaction, and a vanished target aborts it — legacy allowed one vote ever, and parallel votes must not lose a point.
- Contribution points are recomputed by a job coalesced per user on every trigger, never incremented — the spec's "incremental on votes" would drift against a concurrent recompute.
- Locks are managed by `judge.change_comment` — legacy had only the Django admin.
- Org-private and unpublished posts never reach feeds, the homepage, other users' tabs or outsider votes; feeds are a signed-out viewer's view — legacy leaked them through the feed, the sitemap and `vote_blog`.
- Posts render in the new `blog` style, comments in `user` — legacy `blog` was a sanitized staff style and `comment` safe mode; posts are strangers' HTML, so `solution` is not safe enough.
- `blog` sanitizes author HTML first and splices KaTeX in afterwards through nonce slots — KaTeX output carries inline styles the sanitizer must otherwise allow, which would let authors forge overlays.
- `blog` author CSS is strict (no `position`, offsets, `transform`, `z-index`, `opacity`, negative margins or viewport units; unit allow-list; `user-` class prefix; no author MathML or SVG; iframes only YouTube/Vimeo, sandboxed) — a post must not cover the page.
- The frontend must contain every user-authored HTML container (`overflow: clip; contain: paint; isolation: isolate; min-width: 0; contain: inline-size`, `.katex-display { overflow-x: auto }`) — in-flow overflow cannot be stopped by the sanitizer; this covers posts, comments, profile and organization `about` and ticket messages.
- User-authored KaTeX (`blog`, `user`): `maxExpand` 50, `maxSize` 50, sizes beyond ±50em refused on the parse tree, parametered macros refused (hex colours allowed only after colour commands), 20k parse-node cap, 500 ms of KaTeX per render in total (the first formula past it is a `math-error`, later ones show as source) — a stranger's `\def` chain cost seconds per formula; worst accepted formula is about 350 ms.
- `katex` is pinned to exactly 0.19.0 — the size and node checks call the internal `katex.__parse`.
- `font-size` multipliers scale after the size check — accepted, container containment covers the overflow.
- Muted users cannot write or edit posts; staff do not bypass the 10-solve gate — muting silences public text; legacy let superusers only bypass.
- `publishOn` may be set on create (default now) — legacy overwrote it, which made scheduling impossible; a scheduled post is announced on Discord only once published.
- Deleting a post deletes its votes, comments and lock — legacy orphaned the comments; a comment created during the delete may survive unreadable (its page is 404).
- Blog writes are limited to 10 per hour per user, comments to 10 per 5 minutes, votes to 60 per minute across posts and comments — legacy had no limits; moderators share the blog budget.
- Official-contest mode closes comment pages, posting, editing, comment votes and blog writing for non-superusers (moderation routes refuse before writing); blog reads and votes stay, and post delete is not locked (intentional, legacy parity) — legacy hid the comment area and the editor.
- Recent comments scan at most 10 batches of 2 x the page size with one contest scope and continue by id — bounded work even when most recent comments sit on unreadable pages; the anonymous slice is cached 60 s.
- Homepage contests come from `GET /contests?phase=`, not `/home` — one source for contest lists.
- Feeds (blog, comments, problems) carry 25 items, cached 5 minutes, chronological — legacy fed every post with sticky ones first.
- The data export keeps hidden own comments (legacy) and adds own and co-authored posts, streamed — a large history must not sit in memory.
- The `discord.webhooks` setting maps legacy event names (`default`, `on_new_comment`, ...) to https URLs (http for localhost outside production); the URL is read from the setting by the worker, never in job data or logs; payloads allow no mentions, a 4xx is not retried and redirects are refused — a bad URL must not retry-storm or leak the token.
- Discord announcements: comments only for pages a signed-out viewer can read, posts only when published and personal — the channel may be public; organization and suggested problems announce their name and a statement excerpt on create (spec, legacy content); a problem's announcer is its creator — in suggest mode the suggester, otherwise a curator, where legacy used `suggester or authors.first()`.
- `CommentResponse.canEdit` is true for a muted author whose edit is then 403 — muting is rare and the viewer's document is not read per page.
- Accepted residuals: unhide's parent check is read-then-write (a racing hide can leave an orphan), and hide/unhide of a subtree is not one atomic step.
- Comments map legacy `p:`/`s:`/`c:`/`b:`/`t:` pages to entity ids, build `path`/`threadId` from MPTT and render `bodyHtml`; posts render `contentHtml`/`summaryHtml`; `users.contributionPoints` are recomputed after the backfill — reads never render and one job writes the points.
- `judge.change_settings` is operator-grade (grant it to superusers only): webhook and pwned URLs are admin-set, so in production they must be https and may not be `localhost` or a literal loopback/private/link-local IP, and the pwned fetch refuses redirects; the accepted residual is a hostname that resolves to an internal address (blind SSRF, an operator could already reach it).
- Registration takes one optional `organizationId` (open and listed only, never private or unlisted) and `languageId`; legacy allowed several open organizations without the unlisted filter — a signup must not reach hidden schools, more are joined afterwards through the usual membership caps. `activate/resend` always answers 204 and is limited per IP and per email so it cannot enumerate accounts or flood mailboxes.
- Comment `body` is returned only with `canEdit`, so the edit form never needs a second request and readers never get sources.
- Moderators (`judge.change_comment`) get hidden comments in page listings and `locate`, flagged `hidden` with `hiddenBy` (new `hiddenByUser`; null for hides migrated from the old site); everyone else never does — a moderator must see what they hid to unhide it.
- Hide and unhide write `revisions` rows (`hide`/`unhide`) as the audit; the public history lists only `edit` rows.
- Comment delete is soft: `deletedAt`/`deletedBy`, `body` becomes `[deleted]`, `bodyHtml` empty; the row stays in its thread as a placeholder (author and score kept) so replies and quotes keep their context. Deleted comments take no edit, vote, reply or report, leave page counts, recent comments and the author's contribution, and their edit history (which holds the text) becomes moderator-only; a `delete` revision keeps the old body.
- `postBlock` comes from one rule (`postBlockOf`: signed out, contest, locked, muted, needs solved, in posting's order) used by the listing and by posting, so the reason shown is the refusal posting would give; `pageLocked` is the raw lock for everyone (non-overriders already see `locked`).
- Preview renders through the same `renderCommentBody` as posting and editing, 30 a minute per user; reports are once per user and comment (unique index), 10 an hour, settled per comment (`resolved`/`dismissed`), and leave hiding or deleting to the usual routes.
- `Comment.number` comes from a per-page `commentPageCounters` row seeded with the page's comment count on first use; the one-off worker job `comment-numbers-backfill-v1` numbers older rows 1..count by `_id` — posts during the backfill go after them. Rows written without a number after a page's counter exists (an old api during a rolling deploy) could collide; accepted, the deploy restarts every api at once. To re-run, remove the job and restart the worker.

## Tickets and site content

- Ticket messages are limited to 30 per 10 minutes per user (and tickets to 5): legacy had no limit and each message fans out to SSE and Discord.
- Ticket notes are visible to everyone who can read the ticket (legacy parity) and editable only by assignees and `change_ticket` holders.
- Activity session keys are `sha256` hashes (anonymous visitors: hash of address and agent) so a log or dump never holds a usable session id.
- The user agent is classified by a small in-house function (desktop, mobile, tablet, bot): coarse is enough for the staff view and it avoids a dependency.
- Legacy `userActivity` and `userSessions` are not migrated: they are unbounded and v2 expires them after 90 days; `users.lastAccess` and `users.ip` come from the profile.
- Misc config is served publicly through `GET /site` (legacy parity), so it must never hold secrets.
- Flatpages render in the `blog` style, the sanitised staff-HTML style, not `solution`: staff pages stay contained like posts.
- Flatpage urls match `^[-\p{L}\p{N}_/.~]+$` (Django's Unicode `\w`, so Vietnamese slugs round-trip): no query, fragment, dot segment ambiguity or encoded tricks reach another page.
- `judge.change_miscconfig` is operator-grade: the analytics snippet and announcement are raw staff HTML served to every visitor, so grant it like `judge.change_settings` (superusers only).
- Tickets map `content_type` to `linkedItem.type`, inline `general_issue.issue_url` into `generalIssues`, embed messages ordered by time (more than 500 imported whole and reported), copy assignees and `is_contributive`, render bodies in the `user` style, and stamp v7 ids with the legacy creation time so `_id` order stays newest-first; flatpages copy `registration_required`, strip the trailing slash from `url` and render `content` with the `blog` style (legacy urls with non-ASCII characters are accepted by the admin charset); navigation items copy `order`, `parent_id` and `hidden`, and each `regex` is checked with `new RegExp` (legacy Python `re.VERBOSE` patterns need whitespace and comments stripped, or are reported); misc config keeps the last row per key (`home_page_top` and `top_notification` are Django templates rendered by `render_django`: convert or report them); the backfill syncs indexes, and `migration-recompute` recomputes contribution points so good tickets count. Judges are not migrated: judge-v2 registers fresh.
- Ticket `open` filters both ways; absent means both — the closed-ticket view needs `open=false` and the default list must not change.
- Flatpage preview is its own route (`flatpages.change_flatpage`) rather than loosening the problems preview, which needs `edit_own_problem`; it shares the `render-preview:user:<id>` budget with the statement preview, so one per-user limit covers both.
- Flatpage revisions answer 400 for a malformed page id, but the existing `/pages/:id` routes keep 404 — the ruling kept the older routes unchanged rather than align them.
- Notifications: one unread row per user and `groupKey` (partial unique index), a repeated event merges into it and moves it to the top by `lastActivityAt`, a concurrent insert that loses on E11000 retries as a merge (up to 3 attempts) — the row is unique by construction.
- `NotificationsService` lives in `libs/community`, not an api module — the worker writes rows too; it never throws, so a notification problem never fails the write that caused it.
- The fan-out job keeps the last 20 announcement ids on the row (`refs`, indexed with `user`), skips users whose row, read or unread, already has the id, and orders text by the announcement's `createdAt` with `$max` — a BullMQ retry or reordered run neither double-counts, reopens a read row, nor puts older text on top; a user whose insert loses to a racing writer is merged again (3 rounds) and the text step always runs; rows expire 90 days from processing time; a resend reuses the id and so notifies only users not yet reached.
- Inbox writes under impersonation are 204 no-ops — a superuser must not clear the impersonated user's unread state, and the UI must not error.
- The inbox keeps 90 days after the last activity and 500 rows per user (nightly trim of every user over the cap, found by count) — a pointer list, not an archive; no per-user mute in v1.
- Ticket timeline entries are `$push`ed with `$slice: -200` in the same `updateOne` as the state change (compare-and-set on the changed fields, 409 `conflict` when it moved) — a full timeline drops its oldest entry instead of refusing the change; the detail keeps `messages` and adds a merged `timeline` (wire fields never change).
- `lastMessageByStaff` is stored on the ticket, not derived — who counts as staff changes over time; a ticket that predates the flag counts as waiting until its next message.
- Migrated tickets lack `lastMessageByStaff` (raw bulk write, no schema defaults), so `awaitingStaff` counts `lastMessageByStaff: {$in: [false, null]}` — a missing field matches null.
- Ticket alerts reach `change_ticket` holders for tickets nobody is assigned to, but not superusers (they hold every permission) and at most 100 — an alert to every superuser or every moderator would be noise; `users` is indexed on `permissions` and `groups` for the lookup.
- A removed assignee's unread inbox rows for the ticket are marked read (except the owner's own), and a newly assigned user is alerted — the spec only listed removal.
- Canned replies are capped at 100 and listed in one page; `{tên}`/`{bài}` are replaced in the SPA — no server templating, no injection surface.
- The canned-reply cap is a count-then-insert, so concurrent creates can briefly exceed 100 — staff-only, harmless, no lock for it.
- A canned reply's automatic `order` (last + 1) is not bounded by the explicit `order` maximum of 10000, so `nextOrder` can exceed it — only reachable by placing a reply near 10000 first.

## Settings

- Non-infrastructure env became admin settings in one typed registry (`libs/settings/src/registry.ts`), edited at `/api/internal/admin/settings` — operators change SMTP, social login, webhooks and limits without a redeploy; env keeps infrastructure and key material.
- Secrets are sealed with `ENCRYPTION_KEY`: `secret: true` encrypts the whole value, `secret: ['clientSecret']` those top-level fields; the AES-GCM helper moved to `libs/common` — `libs/auth` reads settings and sits above `libs/settings`, so the helper cannot stay in `libs/auth` (no lib cycle).
- `SettingsService.get` is synchronous over an in-memory snapshot (change stream plus one-minute resync, like every querier); `set` runs in one Mongo transaction (read, combine, validate, seal, upsert, revision) and updates the writer's snapshot at once — parallel patches of one setting cannot lose a field and a hot path pays no query.
- PATCH merges fixed-shape object settings (`auth.*`) and replaces maps and scalars; `null` is refused (`RefuseNullFieldsPipe`), clear with `{}`, `''` or `enabled: false` — an admin who cannot see a stored secret can still change the other fields.
- Admin `GET` returns secrets as `{ set: true }`, revisions (`settingRevisions`: before, after redacted, `changedFields`, actor) never hold a clear secret, and a validation error never echoes the input — a secret leaves the server in no response, row or log.
- An unreadable stored value (corrupt row, rotated `ENCRYPTION_KEY`, key dropped from the registry) falls back to the default with a key-only warning — one bad row must not take the process down.
- There is no env fallback and first boot runs on registry defaults; importing old env values is a migrator step (paused) — two sources for one value would disagree silently.
- `mail.smtpUrl` defaults to `''`: mail is not configured and sends fail as 503 `mail_unavailable`; the mailer keys its transport by the URL and closes the old one, OAuth providers are built per call from the settings — a change applies at once, a disabled provider 404s at `start` and `callback` straight away.
- A social signup started before its provider is disabled may still complete within its 10-minute window — accepted: the state and the pending cookies already bound it to that browser.
- `auth.pwnedApiUrl` `''` turns the breach check off, a failing check fails open as before; the test harness switches it off — no network in tests.
- `site.timeZone` (default `Asia/Ho_Chi_Minh`, an IANA name) is a setting and the time-zone helpers live in `libs/common` — the settings validator needs them below `libs/settings`.
- `AppError` carries `extra` members beside `code` and `message` (`banReason` on a banned login, B8) — the SPA never parses a message.
- Validation failures add `issues: [{ field, code, message }]` next to `fields` (B10): codes are the constraint name in snake_case, a decorator `context: { code }` or a code a service names (`username_taken`) — `fields` stays for old clients and the SPA maps codes to its own texts.
- Submit refusals have their own codes (B9): `banned_from_problem`, `contest_submission_limit`, `unfinished_submission_limit` (429), and `solve_first` / `contest_running` / `hidden` on submission detail and source (B18); an `if-solved` problem in a contest whose list is closed answers `contest_running` (including an ended contest with a hidden scoreboard), because solving would not help.
- `GET /auth/username-available` (B11) shows what registration's "Username is taken." already shows, 30 per 10 minutes per IP; a stale pending signup reads as available because registration reclaims it.
- Resend (B16): pending = inactive, not banned, never logged in; sends in the background and answers 204 alike for unknown, active and pending emails, limited per IP and per email — no enumeration, no mailbox flooding. A pending account older than 7 days can still be reclaimed by a later registration of the same name.
- The session carries `siteTheme`, `appearance`, `languageId` (B2) and, before the second factor, `twoFactor: { username, methods }` (B14) with `user` null — the SPA draws the second-factor page without learning more. `siteTheme` defaults to `auto` and is checked by shape only, theme ids belong to the SPA (B3).
- Leaderboards carry `rating` and the first listed `organization` (B5), problems filter on `solved` (B6), the homepage `counts.contests` counts what an anonymous visitor sees (B15).
- The problem detail names the viewer's current contest and attempts left (B19), the submission detail carries `totalCases` counted from the problem's `C` rows, null when case results are hidden (B21).
- `GET /problems/:code/pdf` answers 202 `{ status: 'rendering' }` with `Retry-After: 3` and `no-store` while it renders and 200 `application/pdf` on the same URL afterwards (B20); only enqueueing spends the per-IP render budget, so polling is free — the button polls one URL instead of a wait page.
- `npm run seed:e2e` is an api-side script (`apps/api/src/seed/`) that upserts by natural key and refuses unless `NODE_ENV` is `test` or `development` (B23); the e2e problem is `e2e_sum` (the code `e2e-sum` fails the code pattern) — real-backend frontend tests need known users and a problem without a hand-built database.
- Submission stats (B24) count only what a signed-out viewer may see, with hinted count queries so yesterday's rows are never read — a public counter must not leak private or frozen rows.
- Not done: B4 (a `ranking` event on `contest-events`) and B22 (structured samples, tied to the problem-editor work); B7 (weekly top board) dropped — legacy had none (`judge/views/blog.py` shows top PP and top contributors only), the SPA already shows "Top rating" from the leaderboard, and a weekly figure needs a new per-submission aggregation with no legacy parity.
- Settings restore patches the revision's `before` minus sealed fields; whole-secret keys answer 409 because revisions never hold secrets, and the current secret is kept.
- Setting `default` is redacted like the value, so a secret default never leaks through `GET`.

## Similarity

- Dolos (`@dodona/dolos-lib` 3.5.1, MIT) instead of MOSS — no external service or key, code stays on our servers, same winnowing family.
- Engine in a child process — the library is ESM-only with native tree-sitter addons (Jest and the CJS build cannot load it); the parent kills the child on the deadline and on worker shutdown.
- V8 heap cap of 2 GiB on the child, not a hard cap — native parser memory is outside the V8 heap and bounded only by the container; the 30 minute deadline and the cap are constants, not settings (revisit with real data).
- The child resolves `dolos-lib` itself — no dependency on the worker's working directory.
- `getPair` on candidate pairs, never `allPairs()` — `allPairs` builds all N x N pair objects (800 identical files: 17 s and 310 MB against 2.7 s and 160 MB); candidates are files sharing a fingerprint with a different owner.
- Same-user pairs never built or stored — the spec forbids them and it shrinks the work for resubmitters.
- C and C++ are one family (C++ grammar) — C is close to a C++ subset, so C pasted as C++ is caught; other cross-language copies stay out of scope.
- Pascal compared as text — Dolos has no Pascal grammar and the site uses Pascal; weaker on renamed identifiers; Kotlin, Haskell, Ruby, Perl, Lua, Fortran, Assembly and the non-code languages are skipped and listed in `unsupported`.
- CE, IE, AB, RJ and unjudged submissions are excluded — sources that never ran or were rejected carry no signal; a copied wrong solution is still a copy, so WA, TLE, MLE, RTE, AC and partials are compared.
- Newest 3000 submissions per problem and family — bounds memory and time (3000 identical files is 4.5 million pairs).
- Limits as admin settings snapshotted into the run — operators tune them without a deploy and a run shows what applied; `maxPairs` caps a run, not a group; 50 fragments per pair cap the output.
- A failing group is skipped and flagged `failed: true` — one bad group must not lose the others' results.
- One active run per scope by a partial unique index — two racing starts cannot create two runs; an abandoned run never overwrites results.
- Stale release at the next start: a run queued 3 hours (by `createdAt`) or running past the 30 minute deadline plus 10 minutes (by `startedAt`) is abandoned — queue wait alone no longer discards a run that is legitimately running.
- A success deletes the earlier runs and pairs in one transaction, a failed run keeps them — staff never see a half-written set.
- A stalled redelivery fails the run, and a worker shutdown mid-run fails it (`internal_error`) keeping earlier results — the scope is freed at once; cost: one manual re-run after a deploy.
- Rate limit of 10 starts per user per hour, given back on 409 or an enqueue failure — a refused start costs nothing.
- Unknown, not-visible or not-editable scope is 404, missing permission 403 — nothing tells staff which problems or contests exist; legacy answered 403 to a visible, non-editable contest.
- Pair sources follow the normal submission source rules per side and the list omits problems the viewer cannot see — one source of truth for source secrecy (`SubmissionsService.viewable`), including the contest anti-cheat block.
- Pair list problem-only and language-only filters (and a contest viewer's visible-problems narrowing) read through the `{run, similarity, _id}` index and filter after, bounded by the run's `maxPairs`; only no filter and problem + language are served page-for-page.
- `judge.moss_contest` codename kept — migrated groups already carry it.
- Legacy `judge_contestmoss` rows and the `contestMoss` collection are not migrated (migrator: no mapper) and the old rows stay in the database unreachable — the result URLs on Stanford's server have expired.
- Worker image and CI need `python3`, `make` and `g++` (tree-sitter grammars compile at `npm ci`); the worker runs one similarity job at a time.

## Deploy

- Worker image needs pandoc >= 3, util-linux `prlimit` and Chromium; plan about 2 GB of memory per job of concurrency — PDF and Polygon conversions are memory hungry.
- API and worker mount the same `MEDIA_ROOT`, `PROBLEM_DATA_ROOT`, `PDF_CACHE_ROOT`, `CONTEST_DATA_ROOT` and `USER_DATA_ROOT`; `PROBLEM_DATA_ROOT` and `PDF_CACHE_ROOT` are not checked against `MEDIA_ROOT` at boot, only `CONTEST_DATA_ROOT` and `USER_DATA_ROOT` are; none of the four data roots may sit under it, and `USER_DATA_ROOT` and `CONTEST_DATA_ROOT` must not overlap — it is served publicly.
- nginx: `proxy_buffering off` and a long `proxy_read_timeout` on `/api/internal/events/`; set `TRUST_PROXY` to nginx's address — streams need it, per-IP limits are meaningless otherwise.
- SSE per-IP cap stays 16; `SSE_IP_ALLOWLIST` (IPs/CIDRs) gets 512 for school labs behind one NAT — a blanket raise would let one machine hold hundreds of streams.
- Production: systemd units (api, bridge, worker under `qhhoj.target`) behind host nginx (`deploy/`), not Compose — no Dockerfile, nginx reads dist and `MEDIA_ROOT` from disk, Chromium/pandoc/`prlimit` are simpler on the host; one bridge instance; all sessions are invalidated once at cutover.
- pandoc comes from the official static release (pinned, sha256-checked in CI), not apt: the Debian/Ubuntu build dies with "failed to create OS thread" under `prlimit --as=768MiB` while the static one runs down to 192 MiB; `assertAvailable` reports a start failure verbatim and says "not installed" only for a missing binary.
- Submission stats are cached 30 s in Redis under a zone-agnostic key (`submissions:stats`), so a `site.timeZone` change or the midnight rollover can lag up to 30 s.
- OpenAPI response schemas come from the swagger CLI plugin (`*.dto.ts`/`*.response.ts`), wrapped in `{ data }` by `envelopeResponses`; plain jest cannot run the plugin (and needs isolatedModules off), so `npm run test:openapi` has its own config and the main suite ignores `openapi.e2e-spec.ts`. A new JSON route without a response class fails that spec.
- `openapi.json` is committed and emitted offline (`npm run openapi:emit`: controllers only, providers stubbed, same jest + swagger plugin config as `test:openapi`); a CI job fails, with the diff, when it is stale. The frontend snapshots it and generates `schema.d.ts` with `openapi-typescript`, so a DTO change that breaks a page fails the frontend typecheck, not production. Enums come from `const` arrays, never union types, because the plugin orders a union by compiler type ids, which differ between a cached and a fresh compile.
- Every operation carries a `default` ErrorResponse (`errorResponses`), SSE routes document their frames as a `oneOf` (`ApiEventStream`, no `discriminator` keyword because `openapi-typescript` 7 rewrites the tag), and the swagger plugin's blind spots (initializers without a type, union aliases) are caught by `schema-quality.openapi-spec.ts`.
- Ticket lists look up the editable problems' ids (`visibleIds`, also for `edit_all_problem`) and filter on `linkedItem.id`: index-backed, and a ticket of a deleted problem stays unreadable exactly as `canSee`. Cost: one `distinct` of up to every public problem id per list for `edit_public_problem` holders; denormalize a `problemPublic` flag on the ticket if it gets slow. An unfiltered staff list counts from metadata (`estimatedDocumentCount`), as `countDocuments({})` scans.
- A staff `GET /problems/:code/tickets` on a private problem is 404 (legacy `get_problem_or_404` parity); staff use `GET /tickets`.
- Tickets: filing and posting need only "not muted" (`TicketGateService`); anyone who `canSee` a ticket may post, closed or not. The 500-message cap sits in the `$push` filter (409 `conflict`), creation 5 and messages 30 per 10 min per user (429 `rate_limited`, hit released on a refused write). Events carry ids only; Discord `on_new_ticket*` fire for every ticket.
- Ticket streams judge every event with the viewer's current access (fresh ticket + problem read); a removed permission, ban or session end takes effect at the next stream recheck (<= 60 s by default), like the other channels. Frames are ids only. Events beyond the per-process backlog (`ticketBacklog`) are dropped, then one `resync` frame tells clients to refetch.
- `GET /site` (misc config + official mode) is public and `Cache-Control: private, max-age=60`: the auth guard can set a refreshed session cookie on any request, so a shared cache must never store it. Misc config is served to everyone: never store secrets there. Flatpages are served from the stored `contentHtml`; `registrationRequired` pages answer 401 to anonymous readers, unknown or odd urls 404.
- User activity is captured by a Fastify `onResponse` hook (registered in `UserActivityCaptureService.onModuleInit`, no awaits) into a 5000-row buffer (oldest dropped and counted past it), flushed at 200 rows or every 2 s and on shutdown; a failed or hung (10 s) flush drops its batch, never a response. Paths are stored query-stripped with credential routes (`/public-rankings/<token>`, `/reset-password/<token>`, `/activate/<key>`, also in referers) redacted via `CREDENTIAL_ROUTES` in `libs/community/src/user-activity.ts`, `/site` and `/auth/me` are not logged, an impersonated request is logged as the impersonator (the target's `lastAccess`/`ip` stay untouched), and `users.lastAccess`/`ip` are written at most every 5 min per user (`user-access:<id>` SET NX EX). Live sets `active:*` hold the last 30 min, at most 50,000 members each.
- Staff activity logs sort by `{at:-1}` only (no `_id` tie-break): every filter is then an index scan with no blocking sort, at the cost of rows sharing a millisecond possibly repeating across a page boundary. Lists return `hasMore` without a total (`HasMorePageMetaResponse`). The CSV export streams a cursor in 1000-row chunks, at most 100,000 rows, fixed filename, `no-store`. Deletes are by one user or the anonymous set only, never by free filter, and log who, whom and counts.
- Staff edit flatpages and misc config through `api/internal/admin/site/*` (legacy Django permission names, so migrated groups keep them). Flatpage Markdown is rendered in the sanitised `blog` style (admins cannot embed raw HTML, foreign iframes or fixed overlays; widen later); urls match the Unicode legacy charset `[-\p{L}\p{N}_/.~]`, every page write is a `revisions` row, last write wins. Queriers apply `delete` change events so other processes drop a deleted row at once; the writing process resyncs after each write. Flatpage reads are `Cache-Control: private, no-cache` (the body depends on the session).
- Querier snapshot loads (`loadAll`: whole-collection `find` of a tiny registry) carry the comment `SNAPSHOT_LOAD_COMMENT`, and `profileQueries` drops exactly those entries: the resync crons (settings every minute, catalogs and groups every 10) fire on the wall clock and would otherwise fail index tests by chance.
- Judge link connection caps (bridge w4 review I1): a socket counts as unauthenticated whenever no session is open on it (re-armed 15 s deadline), a judge keeps one socket and one pre-Hello session (helloed sessions are still replaced at the newer Hello, protocol scenario 34), a forced disconnect revokes all sessions and sockets of the judge, and failed key checks are limited per address in memory — no Redis, single bridge instance.
- nginx for the VNOI additions (outside this repo, mirrored in `deploy/nginx/qhhoj.conf`): `location /s/` proxies to the api (the 302 and `Cache-Control: no-store` pass through) and `location /api/sync/` proxies without `Origin`/cookie handling; `TRUST_PROXY` must be set so each client's CIDR check sees its real address, which must be in the key's `allowedCidrs`; the `qhi_` key is a bearer secret, so TLS terminates in front of it.
- Judge hosts: dedicated, SMT and swap off, THP off, performance governor, cgroups v2, isolate 2.6 with its cg keeper; ASLR stays 2 (the one accepted `isolate-check-environment` waiver). Unit with `ProtectSystem=strict` and `RestrictSUIDSGID=yes`, but no NoNewPrivileges (setuid isolate), no SystemCallFilter/SystemCallArchitectures (inherited by isolate and sandboxed programs; isolate needs @mount/@privileged; isolate 2.6 seccomp kills 32-bit binaries, so GAS32 is not supported), and `UMask=0022` (the sandbox uid reads the box files) with `CacheDirectoryMode=0700` — checked by `deploy/judge/check-host.sh` and judge-v2 `packaging/check-unit.sh`.
- Old-site migration finished 2026-10-10 (site live); the migrator app, `qhhoj-migrate`, the worker `migration-recompute` job and the legacy fixtures were removed so nothing can re-run a destructive import; history is in git. Decisions above that name the migrator describe what it did.
