# Production runbook

Files: `nginx/qhhoj.conf`, `nginx/security-headers.conf`, `nginx/qhhoj-gate.conf`, `quadlet/*`, `qhhoj-deploy`, `ci/*`, `env.production.example`, `judge/*`, `backup/*`.
Layout: image `ghcr.io/qhhoj/backend-v2` run by rootful podman quadlets (`/etc/containers/systemd/`, host network, uid/gid 987); frontend under `/var/www/qhhoj/releases/<version>` with `current`; data `/srv/qhhoj`; env `/etc/qhhoj/env`; nginx, MongoDB and Redis native.
This host is the shared live old-site box (the production host), v2 goes in place; judge-v2 runs on a separate machine. Never stop, restart or reconfigure anything on it that is not QHHOJ's.

## How a change reaches production

1. A PR with a changeset (`.changeset/*.md`, `npm run changeset`; empty for CI or docs) is squash-merged to `main`.
2. `.github/workflows/release.yml` opens or updates the "chore: version packages" PR (bumps `package.json`, writes `CHANGELOG.md`). Merging it makes the next run tag `vX.Y.Z` (`scripts/release/tag-release.mjs`, `npm run release:tag`) and call `deploy.yml`.
3. `.github/workflows/deploy.yml` resolves the ref (`deploy/ci/resolve-ref.sh`, `code-changed.sh`), waits for CI (`deploy/ci/wait-for-ci.sh`), then builds the image from `Containerfile` (entrypoint `deploy/container/entrypoint.sh`) and pushes `ghcr.io/qhhoj/backend-v2:vX.Y.Z`.
4. `deploy/ci/remote-deploy.sh` runs `sudo qhhoj-deploy backend vX.Y.Z` over ssh as `deploy`; exit 75 means deferred (a contest is ending) and is retried.
5. `deploy/qhhoj-deploy` (installed to `/usr/local/sbin`) moves the `:current` tag and restarts the quadlet units (`deploy/quadlet/qhhoj-{api,worker,bridge}.container`, `qhhoj.target`); `qhhoj-deploy status` shows the live versions, `qhhoj-deploy rollback backend` goes back.

A release swaps only the image. Quadlets, nginx files, `/etc/qhhoj/env` and `deploy/judge/*` do not travel with it: see "Common changes". The frontend deploys by its own workflow (`qhhoj-deploy frontend <version>`).

## Common changes

- **Memory cap of an app:** edit `MemoryHigh=` and `MemoryMax=` in `deploy/quadlet/qhhoj-<app>.container` (worker 4G/5G, api 1536M/2G, bridge 384M/512M; `deploy/quadlet/quadlet.test.sh` pins the worker value). Merge it, then on the host copy `deploy/` over and run `bash install-host.sh` (idempotent, never starts services), `systemctl daemon-reload` and `systemctl restart qhhoj-<app>`. Plan about 2 GB per PDF job of concurrency.
- **A new or changed env variable:** add it in `libs/common/src/env/` and `.env.example`; document it in `deploy/env.production.example`; set it in `/etc/qhhoj/env` on the host (mode 600, unquoted `KEY=value`); restart the units that read it. Each app validates env at boot and refuses to start on a bad value. Anything an operator changes at runtime is an admin setting instead, not env.
- **An nginx change:** edit `deploy/nginx/qhhoj.conf` (or the snippets), install it as in "First install" step 5, then `nginx -t && systemctl reload nginx`. The Cloudflare ranges: "Cloudflare origin gate".
- **The judge copies:** `deploy/judge/*` are copies of judge-v2 `packaging/`. After touching either side run `scripts/judge/check-deploy-copies.sh ../judge-v2`; a judge release itself is installed on the judge machine ("Judge hosts", "Judge connection").
- **A hot fix of a bad release:** `qhhoj-deploy rollback backend` (seconds), then fix forward through the chain above.

## Prerequisites

- podman >= 4.9 (Ubuntu 24.04 package; installed beside Docker, host network only), nginx >= 1.25.1 (older: `listen 443 ssl http2;`), MongoDB 8 as a replica set `rs0` with auth, Redis >= 7, `mongosh`, `mongodb-database-tools`, `rsync`, `openssl`, `restic` (Backups). The worker toolchain (Node, pandoc, Chromium) is in the image; about 2 GB per PDF job plus 2 GiB for similarity.
- Disk: `MEDIA_ROOT`, `PROBLEM_DATA_ROOT`, `PDF_CACHE_ROOT`, `CONTEST_DATA_ROOT`, `USER_DATA_ROOT` as separate directories under `/srv/qhhoj` owned by uid/gid 987 (none under `MEDIA_ROOT`).
- TLS certificate for the site host; firewall: 80/443 public; `PORT` (3000) closed to everything but loopback (the api also binds 127.0.0.1 via `LISTEN_HOST`); `JUDGE_BRIDGE_PORT` from judge hosts only.

## Cloudflare origin gate

The qhhoj server blocks answer 444 (close, no reply) to any TCP peer that is not Cloudflare or loopback, so knowing the origin address does not bypass Cloudflare. It is per server block: other sites on the shared host (e.g. `kd.tiepluatrithuc.com`, served directly) are untouched; do not use a firewall rule for this.
- Needs `/etc/nginx/conf.d/00-cloudflare-real-ip.conf` (`set_real_ip_from` per Cloudflare range plus `real_ip_header CF-Connecting-IP`): the gate tests `$realip_remote_addr`, the TCP peer.
- Apply: install `deploy/nginx/cloudflare-origin.conf` as `/etc/nginx/conf.d/qhhoj-cloudflare-origin.conf` (`install-host.sh`), put the new `qhhoj.conf` blocks in place (each has an `if ($qhhoj_refuse_origin) { return 444; }`), then `nginx -t && systemctl reload nginx`. Check: `curl -sI https://qhhoj.com/` works; from outside Cloudflare `curl -sk --resolve qhhoj.com:443:<origin-ip> https://qhhoj.com/` gets an empty reply; from the host `curl -sk --resolve qhhoj.com:443:127.0.0.1 https://qhhoj.com/` works (qhhoj-deploy's frontend check uses it).
- Rollback: delete the two `if ($qhhoj_refuse_origin)` blocks (or the `return 444;` lines), `nginx -t && systemctl reload nginx`.
- Refresh the ranges (Cloudflare adds some rarely; also refresh `00-cloudflare-real-ip.conf`): fetch `https://www.cloudflare.com/ips-v4` and `/ips-v6`, rewrite the `geo` entries (`<range> 1;`) and the date in the file header, install, `nginx -t && systemctl reload nginx`. A stale list answers 444 for a new Cloudflare range, so refresh every few months.
- ACME http-01 (`/.well-known/acme-challenge/`) passes the gate on port 80, but the port-80 block only redirects to https: renew with a method that works through that (DNS-01, or certbot's nginx plugin) as before.

## First install

1. Install the packages above (this host: see "History: 2026-10 cutover", In-place on the shared host).
2. Copy `deploy/` to the host (`scp -r deploy root@host:/root/qhhoj-deploy`) and run `bash /root/qhhoj-deploy/install-host.sh`. It is idempotent: creates the users `qhhoj` (uid/gid 987) and `deploy`, the directories (`/srv/qhhoj/*`, `/etc/qhhoj`, `/var/lib/qhhoj-deploy`), and installs the helper scripts, quadlets and sudoers; it never starts services. It refuses if uid/gid 987 is taken by another account (then rebuild the image with `--build-arg QHHOJ_UID=<free id>` and change `ID` in the script). Let nginx read the data group: `usermod -aG qhhoj www-data` (`nginx` on nginx.org packages), then restart nginx; the image entrypoint (`deploy/container/entrypoint.sh`, `umask 0027`) keeps new files group-readable and setgid keeps the group, nginx reads `/media/` through that group (without it every `/media/` request is 403). Only `media` and `/srv/qhhoj` itself are group-readable (2750); `problem-data`, `pdf-cache`, `contest-data` and `user-data` are owner-only (2700), so nginx (in the group) cannot read hidden test data. The local judge `qhhoj-judge` reads `problem-data` through its own read ACL, which `install-host.sh` sets once that user exists: re-run it after creating `qhhoj-judge` ("Judge hosts" step 4), and after any restore or rsync into `problem-data` (it re-applies the ACLs); remote judges read `PROBLEM_DATA_ROOT` through the NFS read export (step "Problem data over NFS"). Never serve `problem-data` from an nginx location. For legacy rsync use `--chown=987:987 --chmod=D2700,F600`, then re-run `install-host.sh`. The CD user `deploy` gets `/usr/local/sbin/qhhoj-deploy-serve` as its login shell (step 6).
3. `/etc/qhhoj/env` from `env.production.example` (mode 600; unquoted `KEY=value`, podman `--env-file` format); `ENCRYPTION_KEY`, `TOKEN_SECRET` by `openssl rand -hex 32`; `MONGO_URL` with the `qhhoj` user from `/root/qhhoj-secrets/mongo.env`; on the shared host `REDIS_URL=redis://127.0.0.1:6379/4`, `JUDGE_BRIDGE_PORT=9990`. Bridge TLS: `chown root:987 /etc/qhhoj/bridge-tls/key.pem && chmod 640` it ("Judge hosts" step 6 makes the pair).
4. GHCR: CD logs in per deploy with the workflow's `GITHUB_TOKEN` (`qhhoj-deploy backend <tag> --token-stdin`), no token on the host. For a manual `qhhoj-deploy backend <tag>` without it: `podman login ghcr.io --authfile /etc/qhhoj/ghcr-auth.json` with a classic token limited to `read:packages` (fine-grained tokens cannot read GHCR), then `chmod 600` it.
5. nginx: `deploy/nginx/qhhoj.conf` to `conf.d/` (on the shared host: the in-place block replacement in "History: 2026-10 cutover") with the `CHANGE` lines, `security-headers.conf` to `snippets/qhhoj-security-headers.conf`, `qhhoj-gate.conf` to `snippets/qhhoj-gate.conf`, `maintenance.html` to `/var/www/qhhoj-maintenance/` (`install-host.sh` does these); `cloudflare-origin.conf` to `conf.d/qhhoj-cloudflare-origin.conf` (`install-host.sh` does that too; see "Cloudflare origin gate"); `nginx -t && systemctl reload nginx`. TLS: reuse the site certificate (copy it from the old host if the host is new until DNS points here), then `certbot` on this host.
6. CD access: `ssh-keygen -t ed25519 -N '' -f /root/deploy_key`, append the public key, forced to the dispatcher, to `/home/deploy/.ssh/authorized_keys`: `printf 'restrict,command="/usr/local/sbin/qhhoj-deploy-serve" %s\n' "$(cat /root/deploy_key.pub)" >> /home/deploy/.ssh/authorized_keys` (owner `deploy`, mode 600; `qhhoj-deploy-serve` allows only `sudo qhhoj-deploy ...` and a write-only rsync into `incoming/`, needs `/usr/bin/rrsync` from the `rsync` package, and logs refusals with tag `qhhoj-deploy-serve`; `/var/lib/qhhoj-deploy` is root-owned, only its `incoming/` is the deploy user's); in both GitHub repos create environment `production` with secrets `DEPLOY_HOST`, `DEPLOY_SSH_KEY` (the private key; then delete it from the host), `DEPLOY_KNOWN_HOSTS` (`ssh-keyscan <host>`).
7. First deploy: run the backend and frontend `deploy` workflows by hand (empty ref); until the nginx block swap the frontend deploy does a file check only (nginx does not serve v2 yet); `qhhoj-deploy status` shows both.
8. Indexes: every backend deploy builds them with the new image before the restart (`.hint()` queries throw without them); a failed build (a unique index over duplicates, or an index whose options changed) fails the deploy and the previous version stays live. By hand: `MONGO_URL=... podman run --rm --network=host -e MONGO_URL -e APP=worker ghcr.io/qhhoj/backend-v2:<tag> indexes`.

## Smoke checks

- `curl -fsS https://HOST/api/internal/site` returns JSON; `curl -I https://HOST/some/spa/route` returns 200 with the HTML shell.
- `curl -N https://HOST/api/internal/events/...` as a logged-in user prints a heartbeat within 15 s without delay (proves unbuffered).
- Log in, open a problem, submit a solution; a judge grades it; the verdict appears live (during the cutover review only once a judge was switched).
- A statement PDF renders (worker + Chromium + pandoc); an uploaded image shows from `/media/`.
- `ss -ltn | grep 9990` is open locally but unreachable from outside the judge machine (ufw); `systemctl status qhhoj-*` all active.
- `curl -sI https://HOST/s/nonexistent` is 404 (not the SPA shell: proves the `/s/` location); an integration key from outside its `allowedCidrs` is refused on `/api/sync/v1/...`.
- Registration works only after `mail.smtpUrl` is set (admin settings, `judge.change_settings`).

## Integration clients (sync API)

- `TRUST_PROXY` must be set behind nginx: each client's CIDR check and the failed-key lockout (20 bad `qhi_` keys in 10 minutes from one address answer 429 for every key from it) use `request.ip`; without it all clients share the proxy's address (the api logs a boot warning when active clients exist).
- Staff reach the integration-client admin through `judge.manage_integration`; superusers bypass it.
- A client's acting user must not be a superuser and must hold `judge.add_contest` and `judge.create_private_contest`; it may hold more than the key's creator, so use a dedicated account. Keys may carry `expiresAt`; each client gets 60 requests per minute.
- nginx needs the `/s/` and `/api/sync/` locations from `deploy/nginx/qhhoj.conf`, plus its `robots.txt`, sitemap, legacy PDF/`/url/` redirects and the preview-bot `map`/`if` (the two `map` blocks sit in the http context above `server`).

## Polygon account

- Create (or reuse) one Polygon account for QHHOJ; in Polygon, Settings -> API keys, create a key. In QHHOJ admin settings (`judge.change_settings`) set `polygon.apiKey` and `polygon.apiSecret` (both stored encrypted, never shown again; a key saved before 2026-10-11 stays readable and is sealed on the next save; after an `ENCRYPTION_KEY` change re-enter `polygon.apiKey`, until then Polygon answers `polygon_unauthorized`) and `polygon.accountName` (its login), then "test connection" (`POST /api/internal/polygon/test`). `polygon_clock_skew` means the server clock is off: check `timedatectl` / NTP.
- Setters add `polygon.accountName` as a READ co-author of their problem, build a full package (with Linux tests) and paste the problem page link (`https://polygon.codeforces.com/p…/owner/name`) under "Import from Polygon" (anyone who may create the problem; syncing it later needs `judge.sync_polygon_problem`). The `p…` part is the permission: QHHOJ compares it with the `url` recorded in the newest package's problem.xml, so treat the link like a password. `polygon_link_refused` means not shared with the account or a wrong link; `polygon_no_package` means no READY package to check against.
- The worker downloads packages from `https://polygon.codeforces.com/api/` (outbound HTTPS from the worker host) and checks auto-sync problems every 10 minutes, skipping problems of a running contest. Emptying the key or secret disconnects; linked problems keep their content. Every finished import and sync (manual or automatic, ok or failed with the step it stopped at) is listed under `GET /api/internal/polygon/syncs` and per problem under `GET /api/internal/problems/{code}/polygon/syncs`.

## Security headers

`security-headers.conf` (HSTS one year, no `includeSubDomains`, no preload) and the SPA's CSP in `qhhoj.conf`, which stays `Content-Security-Policy-Report-Only` (no report endpoint). Its `script-src` hash is `index.html`'s inline pre-paint script; frontend-v2 CI fails while that hash is missing from `qhhoj.conf` on backend main, so a changed script lands its new hash here first (keep the old one until the frontend has deployed), then the block goes onto the host (`nginx -t && systemctl reload nginx`).
- Before renaming it to an enforcing `Content-Security-Policy`: Cloudflare injects its own inline script into the page per request (`/cdn-cgi/challenge-platform/...`, JavaScript detections), which no static hash can cover. Check in a browser console whether an enforcing header blocks it; if it does, either turn JavaScript detections off for the zone or serve a per-request nonce, and check what that costs bot detection. Until then enforcing would only break Cloudflare's script, not the SPA.

## Deploy notes

- Stream caps per api process (fixed defaults, no env override): public submission feed 900 (was 1000), contest event-feed streams 100 (`contestFeedTotal`, new), contest streams 1500, notification streams 2000, total 5000. The caps add up to 4500, which leaves 500 slots for submission and ticket streams. Beyond a cap the api answers 429; with several api processes behind nginx each process counts on its own. A load balancer or monitoring that assumed 1000 feed streams per process needs the new numbers.
- Release flow: every PR carries a changeset (`npm run changeset`; a pure CI/docs PR uses `npx changeset --empty`). A merge to `main` deploys nothing: `release.yml` opens or updates the "chore: version packages" PR (GitHub-signed, so Verified) and dispatches `ci` and `changeset` on `changeset-release/main`, because a PR made with `GITHUB_TOKEN` starts no workflow and the required checks would never report. Merging that PR (a version bump) makes `release.yml` tag `vX.Y.Z`, create the GitHub Release from the changelog and call `deploy.yml` for the tag. The image is pushed as `ghcr.io/qhhoj/backend-v2:vX.Y.Z` and `:sha-<12>`; its `org.opencontainers.image.source` label links the package to the repo.
- CD: a release tag builds the image, pushes it to GHCR and deploys after CI passes (SSH as `deploy`, `sudo qhhoj-deploy`); Actions -> deploy -> Run workflow (from `main` only) deploys a release tag or a commit on `main`; anything else is refused (`force` deploys during a running contest, never without CI). Exit 75 = deferred (a contest ending within 24 h is running, or another deploy holds the lock; a long-running practice contest does not block): retry later; `qhhoj-deploy backend <tag> [--force]`, `qhhoj-deploy frontend <version>`, `qhhoj-deploy rollback backend|frontend` (previous history entry), `qhhoj-deploy status` (live versions and history). A good deploy keeps two backend images and two frontend releases, the live one and the one `rollback` returns to (an image is about 2.3 GB; only `ghcr.io/qhhoj/backend-v2` tags are removed, other projects' images never), so a second rollback in a row finds its target gone and refuses with history unchanged. `frontend` copies the assets of the kept releases that are younger than 14 days into the new release without overwriting (open tabs on the previous build still fetch their old hashed chunks); a rollback switches to the older release as it was. This helper changes only after `install-host.sh` is re-run on the server. A failed health check rolls back by itself. The helper scripts themselves (`qhhoj-deploy`, quadlets, sudoers) update only by re-running `install-host.sh` from a fresh copy of `deploy/`.
- Request bodies over a route's limit answer 413 with error code `payload_too_large` (it was `http_error`).

### Polygon link index (once, before the deploy that adds `polygon_link_problem_unique`)

Purged tombstones keep their old `polygonLink`; clear them so the unique index is not blocked by them: `db.problems.updateMany({ purgedAt: { $exists: true }, 'polygonLink.problemId': { $exists: true } }, { $set: { polygonLink: null } })`. The deploy's index build fails (and the deploy with it) if two live problems share a `polygonLink.problemId`: find them with an aggregation on that field and unlink one. After the new index exists, drop the old one: `db.problems.dropIndex('polygonLink.problemId_1')`.

## Backups

`backup/`: `qhhoj-backup` (installed to `/usr/local/sbin` with `qhhoj-backup-lib.sh`, which it sources), run nightly at 03:30 Asia/Ho_Chi_Minh by `qhhoj-backup.timer`; `restore-test.sh` (installed as `qhhoj-backup-restore-test`); `backup.env.example`. restic: encrypted, deduplicated, incremental, zstd-compressed (repository format 2). No daemon: a oneshot unit capped at one CPU and 2 GiB, at idle priority, because the site and the local judge share the host.

- LOCAL repository (`LOCAL_REPO`, `/backup/restic`): the database only. The disk cannot hold a second copy of `problem-data`; a run is refused (and fails) when its filesystem has less than `LOCAL_MIN_FREE_GB` (3) free.
- OFFSITE repository (`OFFSITE_REPO`, any restic backend: `s3:`, `b2:`, `sftp:`, `rclone:`): the database and `DATA_PATHS` (`problem-data`, `media`, `contest-data`, `user-data`). Unset, the files have no backup and every run says so in the journal.
- PULL copy ("Pull copy (owner laptop)" below): the owner's laptop pulls the database and the same four trees into its own restic repository at 04:30; the host holds no credential that reaches it.
- The database is one `mongodump --archive --oplog` (point in time, uncompressed so restic deduplicates night to night) streamed into `restic backup --stdin`, tagged `qhhoj-db` (+ `oplog`); a failed dump fails the run and its partial snapshot is forgotten. Files are tagged `qhhoj-files`. `pdf-cache` is a cache; Redis holds no durable state (queue truth is Mongo).
- Retention per repository and tag: 7 daily, 4 weekly, 6 monthly, pruned nightly. A failed night's partial snapshot that cannot be forgotten is listed in `/var/lib/qhhoj-backup/stranded-snapshots` (the unit's `StateDirectory`); every run retries the forget first, and retention stays off that repository (the run fails) until it is gone. About weekly (6.5 days after the last one) `restic check --read-data-subset 5%` (offsite: about 1 GB downloaded a week, mind the backend's egress price).
- Failure: the unit ends `failed` (`systemctl --failed`, `journalctl -u qhhoj-backup`), a run still going after 12 h (`TimeoutStartSec`, a stalled backend) too; with `HEALTHCHECK_URL` set (healthchecks.io or alike) it is pinged at start, success and `/fail`, and a missed night alerts too.
- Env in a subshell: the commands below load `/etc/qhhoj/backup.env` inside `( ... )` or a child shell, so `RESTIC_PASSWORD`, `MONGO_BACKUP_PASSWORD` and the backend keys do not stay exported in the root session.
- Secrets: keep `/etc/qhhoj/env` (at least `ENCRYPTION_KEY`, `TOKEN_SECRET`) and `RESTIC_PASSWORD` in an offline secret store, separate from the backups: encrypted settings and 2FA secrets in a dump are useless without the same `ENCRYPTION_KEY`, and no snapshot opens without `RESTIC_PASSWORD`.

### Install (once, as root)

1. `apt install restic` (Ubuntu 24.04: 0.16.4); `mongodump --version` must be 100.3 or newer (`--config` with `uri` and `password`).
2. A read-only backup user. The built-in role `backup` reads every database and the oplog, which `--oplog` needs (the app user `qhhoj` cannot): `mongosh "mongodb://admin@127.0.0.1:27017/?authSource=admin&replicaSet=rs0"` (password in `/root/qhhoj-secrets/mongo.env`), then `db.getSiblingDB('admin').createUser({ user: 'qhhoj-backup', pwd: passwordPrompt(), roles: [{ role: 'backup', db: 'admin' }] })`; add its password to `/root/qhhoj-secrets/mongo.env`.
3. Files: re-run `install-host.sh` from a fresh copy of `deploy/`, or only `install -m 755 backup/qhhoj-backup /usr/local/sbin/qhhoj-backup && install -m 644 backup/qhhoj-backup-lib.sh /usr/local/sbin/qhhoj-backup-lib.sh && install -m 755 backup/restore-test.sh /usr/local/sbin/qhhoj-backup-restore-test && install -m 644 backup/qhhoj-backup.service backup/qhhoj-backup.timer /etc/systemd/system/ && systemctl daemon-reload`.
4. `install -m 600 -o root -g root backup/backup.env.example /etc/qhhoj/backup.env` and fill it: `RESTIC_PASSWORD` (`openssl rand -base64 32`), `MONGO_BACKUP_PASSWORD`, `OFFSITE_REPO` and its backend credentials. An `sftp:` repository: `ssh` once as root to the target to accept its host key (the unit sees `/root` read-only and cannot write `known_hosts`).
5. `( set -a; . /etc/qhhoj/backup.env; set +a; case "$RESTIC_PASSWORD" in '' | CHANGE) echo 'set RESTIC_PASSWORD first' >&2; exit 64 ;; esac; restic init -r "$LOCAL_REPO" && if [ -n "$OFFSITE_REPO" ]; then restic init -r "$OFFSITE_REPO"; fi )`: it refuses to encrypt a repository with the example's published `CHANGE` (both scripts refuse it too).
6. First run by hand: `systemctl start qhhoj-backup.service` (it blocks until done; the first offsite run uploads all of `problem-data`), then `journalctl -u qhhoj-backup -n 50` ends with `qhhoj-backup: done`.
7. `qhhoj-backup-restore-test` (and `qhhoj-backup-restore-test offsite`) ends with `restore-test: ok`.
8. `systemctl enable --now qhhoj-backup.timer`; `systemctl list-timers qhhoj-backup.timer` shows the next 03:30 run.

### Check and list

- Monthly, right after a night's run: `qhhoj-backup-restore-test [local|offsite]` restores the newest database snapshot into a throwaway `mongod` (unix sockets only, under `RESTORE_TEST_DIR`, 0.25 GiB cache, removed afterwards; refused unless the archive's size plus `RESTORE_TEST_MIN_FREE_GB` (1) is free) and compares each collection's count with the live database (`RESTORE_TEST_TOLERANCE_PCT`, at least 10 documents; a missing collection fails).
- Snapshots: `( set -a; . /etc/qhhoj/backup.env; set +a; restic -r "$LOCAL_REPO" snapshots --tag qhhoj-db )` (offsite: `-r "$OFFSITE_REPO"`, `--tag qhhoj-files` for files); `restic -r ... ls <id>` lists a files snapshot.
- The throwaway `mongod` (here and in Restore) runs without auth with a full copy of the database, `admin.system.users` included, so it opens no TCP port: it listens only on unix sockets inside its 0700 scratch directory, which only root can reach. Keep those runs short and attended anyway.

### Restore the database

Always into a scratch `mongod` first, then copy only the `qhhoj` database into the live one (the archive is the whole instance, admin users included, and `mongorestore` refuses namespace filters with `--oplogReplay`). Run the steps in a child shell that holds the env and `exit` it after step 5: `bash -c 'set -a; . /etc/qhhoj/backup.env; set +a; exec bash -i'`.

1. Scratch, on unix sockets only (no TCP port: the copy has no auth): `install -d -m 700 /backup/restore/db && mongod --dbpath /backup/restore/db --bind_ip /backup/restore/mongod.sock --unixSocketPrefix /backup/restore --wiredTigerCacheSizeGB 0.5 --fork --logpath /backup/restore/mongod.log`, then `S=mongodb://%2Fbackup%2Frestore%2Fmongod.sock/`.
2. `restic -r "$LOCAL_REPO" dump --tag qhhoj-db latest /qhhoj-mongo.archive | mongorestore --uri "$S" --archive --drop --oplogReplay` (a snapshot id instead of `--tag qhhoj-db latest` for an older night; no `--oplogReplay` for a snapshot without the `oplog` tag).
3. Check it in `mongosh "${S}qhhoj"` (counts, the newest submission).
4. `systemctl stop qhhoj.target`, then `mongodump --uri "$S" --db qhhoj --archive | mongorestore --config <(printf "uri: '%s'\n" "$(sed -n 's/^MONGO_URL=//p' /etc/qhhoj/env)") --archive --drop --nsInclude 'qhhoj.*'` (the app user; the URL stays out of argv, but a failed connection prints it, password included, to the terminal), `systemctl start qhhoj.target`.
5. `mongod --dbpath /backup/restore/db --shutdown && rm -rf /backup/restore`.

### Restore files (offsite)

In the env child shell from Restore the database (`exit` it when done).

- Part of a tree, e.g. one problem: `restic -r "$OFFSITE_REPO" restore latest --tag qhhoj-files --target /backup/restore-files --include /srv/qhhoj/problem-data/<code>`, check it, then `rsync -a --chown=987:987 /backup/restore-files/srv/qhhoj/problem-data/<code>/ /srv/qhhoj/problem-data/<code>/` and remove `/backup/restore-files`.
- A whole tree goes back in place (the disk has no room for a second copy of `problem-data`): `restic -r "$OFFSITE_REPO" restore latest --tag qhhoj-files --target / --include /srv/qhhoj/problem-data`. It overwrites the files the snapshot has and leaves newer ones; owners and modes come back as saved (987, 2700); then re-run `install-host.sh` to re-apply the read ACLs.

### Pull copy (owner laptop)

`backup/pull/`: the owner's Ubuntu laptop pulls a copy nightly at 04:30 Asia/Ho_Chi_Minh (after the host's 03:30 run) into `~/qhhoj-backups/restic`: the database (`ssh qhhoj-pull@host dump | restic backup --stdin`, tags `qhhoj-db`, `oplog`) and `problem-data`, `media`, `contest-data`, `user-data` (rsync `--delete` into `~/qhhoj-backups/mirror`, then `restic backup` of it, tag `qhhoj-files`; restic history keeps what a later night deleted). Retention 14 daily, 8 weekly, 12 monthly, prune, an about weekly sampled `restic check`; a failed dump forgets its partial snapshot as on the host.

Security model:
- The laptop connects out; the host holds no key, password or token for the laptop, so a compromised host cannot reach, change or delete the laptop's copies.
- The laptop's key logs in as `qhhoj-pull` and can only run `qhhoj-pull-serve`: a dump as the read-only `qhhoj-backup` user, `rrsync -ro` of the four trees, or `ping` (a no-op reachability probe); anything else is refused (exit 1) and logged (`journalctl -t qhhoj-pull-serve`).
- A stolen laptop key reads what the backup reads and nothing more, and writes nothing; revoke it by deleting its `authorized_keys` line. The repository is encrypted with a password that exists only on the laptop and offline.

The pull user gets its own root-owned copy of the two `MONGO_BACKUP_*` lines (`/etc/qhhoj-pull/mongo.env`, `root:qhhoj-pull` 640) instead of a sudo helper that reads `backup.env`: it already receives the whole database through `dump`, so the copy grants nothing more, while a sudo rule would add a root entry point and expose `RESTIC_PASSWORD`. A rotated `qhhoj-backup` password goes into both files.

Laptop, as the owner, in a checkout of this repository (key first: the host step needs the public key):

1. `sudo apt install restic rsync` (restic >= 0.16) and `ssh-keygen -t ed25519 -N '' -C "qhhoj-pull@$(hostname)" -f ~/.ssh/qhhoj-pull`; copy `~/.ssh/qhhoj-pull.pub` to the host.

Host, as root (files from a fresh copy of `deploy/`: `install-host.sh` installs `qhhoj-pull-serve` and `qhhoj-backup-lib.sh` to `/usr/local/sbin`):

2. `test -x /usr/bin/rrsync && python3 --version` (Ubuntu 24.04's `rsync` ships `rrsync`).
3. The user, with a root-owned home and `.ssh` so it cannot add itself another key: `useradd --system --no-create-home --home-dir /var/lib/qhhoj-pull --shell /bin/sh --groups qhhoj qhhoj-pull` (sshd runs a forced command through the login shell, so not `nologin`; the locked password only blocks password logins), `install -d -m 755 -o root -g root /var/lib/qhhoj-pull /var/lib/qhhoj-pull/.ssh`.
4. The key, forced to the dispatcher: `printf 'restrict,command="/usr/local/sbin/qhhoj-pull-serve" %s\n' "$(cat /root/qhhoj-pull.pub)" > /var/lib/qhhoj-pull/.ssh/authorized_keys && chmod 644 /var/lib/qhhoj-pull/.ssh/authorized_keys`. With a fixed laptop address add `from="<ip>",` after `restrict,`. If `sshd -T | grep -Ei '^allow(users|groups)'` prints a list, add `qhhoj-pull` to it and `systemctl reload ssh`.
5. Credentials: `install -d -m 750 -o root -g qhhoj-pull /etc/qhhoj-pull && grep -E '^MONGO_BACKUP_(URL|PASSWORD)=' /etc/qhhoj/backup.env > /etc/qhhoj-pull/mongo.env && chown root:qhhoj-pull /etc/qhhoj-pull/mongo.env && chmod 640 /etc/qhhoj-pull/mongo.env`.
6. Read access: `media` is 2750 and read through the group; `problem-data`, `contest-data` and `user-data` are owner-only (2700, kept closed to nginx), so give the pull user alone a read ACL: `apt install acl`, then `setfacl -R -m u:qhhoj-pull:rX -m d:u:qhhoj-pull:rX /srv/qhhoj/problem-data /srv/qhhoj/contest-data /srv/qhhoj/user-data`. Every later `install-host.sh` run re-applies it (its `install -d -m 2700` resets the mode, which masks the ACL entry) and stops if `setfacl` is missing. Check: `sudo -u qhhoj-pull find /srv/qhhoj/problem-data /srv/qhhoj/media /srv/qhhoj/contest-data /srv/qhhoj/user-data ! -readable | head` prints nothing.

Laptop again:

7. `install -d -m 700 ~/.config/qhhoj-backup ~/qhhoj-backups && install -m 600 deploy/backup/pull/pull.env.example ~/.config/qhhoj-backup/pull.env` (edit `SERVER` if needed); `( umask 077; openssl rand -base64 32 > ~/.config/qhhoj-backup/restic-password )` and keep a copy offline; `restic init -r ~/qhhoj-backups/restic --password-file ~/.config/qhhoj-backup/restic-password`.
8. `install -D -m 755 deploy/backup/pull/qhhoj-pull ~/.local/bin/qhhoj-pull && install -m 644 deploy/backup/qhhoj-backup-lib.sh ~/.local/bin/qhhoj-backup-lib.sh && install -D -m 644 -t ~/.config/systemd/user deploy/backup/pull/qhhoj-pull.service deploy/backup/pull/qhhoj-pull.timer && systemctl --user daemon-reload`.
9. Host key: `ssh-keyscan -t ed25519 <host> >> ~/.ssh/known_hosts` and compare its fingerprint (`ssh-keygen -lf`) with the host's `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` (the run uses `BatchMode` and never asks).
10. First run by hand (copies all of `problem-data`): `systemctl --user start qhhoj-pull.service`, then `journalctl --user -u qhhoj-pull -n 30` ends with `qhhoj-pull: done`; on the host `journalctl -t qhhoj-pull-serve` shows `dump` and `rsync ...`.
11. `systemctl --user enable --now qhhoj-pull.timer` and `sudo loginctl enable-linger "$USER"` (the user manager, and so the timer, runs without a login session); `systemctl --user list-timers qhhoj-pull.timer`.

Failure shows as `systemctl --user --failed` and in `journalctl --user -u qhhoj-pull`, with a desktop notification (`notify-send`) when a session is open. Asleep or offline at 04:30: the timer runs at the next wake (`Persistent`); a host the first `ping` cannot reach (or log in to: the journal keeps ssh's reason) exits 75, changes nothing, and the unit retries every 10 min, 4 starts in 2 h, then stays failed; it notifies only when the last good pull (`~/.local/state/qhhoj-pull/last-success`) is over 36 h old. A link lost after that is a failed step (exit 1). Below `MIN_FREE_GB` (20) free the run is refused.

Restore from the laptop (`export RESTIC_REPOSITORY=~/qhhoj-backups/restic RESTIC_PASSWORD_FILE=~/.config/qhhoj-backup/restic-password`):

- Database: `restic snapshots --tag qhhoj-db`; check the archive in a scratch `mongod` on the laptop (the `mongodb-org` package, or a `mongod` binary such as `~/.cache/mongodb-binaries/mongod-x64-ubuntu-8.0.4` plus `mongodb-database-tools`): `mkdir -p ~/qhhoj-restore/db && mongod --dbpath ~/qhhoj-restore/db --port 27999 --bind_ip 127.0.0.1 --fork --logpath ~/qhhoj-restore/mongod.log`, `restic dump --tag qhhoj-db latest /qhhoj-mongo.archive | mongorestore --port 27999 --archive --drop --oplogReplay`, look in `mongosh --port 27999 qhhoj`, then `mongod --dbpath ~/qhhoj-restore/db --shutdown`. To put it back: `restic dump --tag qhhoj-db latest /qhhoj-mongo.archive > qhhoj-mongo.archive`, follow "Restore the database" on the host, `scp` the file into `/backup/restore/` after its step 1, and in step 2 pipe `cat /backup/restore/qhhoj-mongo.archive |` in place of `restic ... dump ... |`.
- Files: snapshot paths are the laptop's mirror (`$HOME/qhhoj-backups/mirror/<tree>`), and owners are the laptop user's. One problem: `restic restore latest --tag qhhoj-files --target ~/qhhoj-restore --include "$HOME/qhhoj-backups/mirror/problem-data/<code>"`, then `rsync -a --chown=987:987 --chmod=D2700,F600 ~/qhhoj-restore$HOME/qhhoj-backups/mirror/problem-data/<code>/ root@<host>:/srv/qhhoj/problem-data/<code>/` (`contest-data`, `user-data` the same), then re-run `install-host.sh` on the host (read ACLs). The newest night needs no restic: the mirror itself is that copy.

## Rollback

A bad release is undone at the deploy level; the old-site rollback of the cutover is in "History: 2026-10 cutover".

- Deploy level (any time): `qhhoj-deploy rollback backend` or `rollback frontend`; `qhhoj-deploy status` shows the live versions. Releases are re-tagged images, so this is seconds.

## Judge hosts

The step-by-step guide for whoever deploys a judge machine is judge-v2 `DEPLOY.md` (shipped in the release tarball; remote judges reach this host over WireGuard, `10.77.0.0/24`). This section is the reference it follows. Dedicated Ubuntu 24.04 hosts, nothing else on them. Per host, as root:

1. Kernel and boot: cgroups v2 is the default on 24.04 (`/sys/fs/cgroup/cgroup.controllers` exists). Turn SMT off (`echo off > /sys/devices/system/cpu/smt/control` and `nosmt` in `GRUB_CMDLINE_LINUX`, `update-grub`), swap off (`swapoff -a`, remove the swap line from `/etc/fstab`), `sysctl -w kernel.randomize_va_space=2`, `kernel.apparmor_restrict_unprivileged_userns=1` and `kernel.core_pattern=core` (persist all three in `/etc/sysctl.d/90-qhhoj-judge.conf`), `apt install unattended-upgrades chrony linux-tools-common linux-tools-$(uname -r)`. Timing stability, persisted by a oneshot unit:
   ```ini
   # /etc/systemd/system/qhhoj-judge-tuning.service
   [Unit]
   Description=Judge host CPU and memory tuning (THP off, performance governor, boost off)
   Before=qhhoj-judge.service isolate.service
   [Service]
   Type=oneshot
   RemainAfterExit=yes
   ExecStart=/bin/sh -c 'echo never > /sys/kernel/mm/transparent_hugepage/enabled; echo never > /sys/kernel/mm/transparent_hugepage/defrag; echo 0 > /sys/kernel/mm/transparent_hugepage/khugepaged/defrag'
   ExecStart=/usr/bin/cpupower frequency-set -g performance
   ExecStart=/bin/sh -c 'if [ -w /sys/devices/system/cpu/cpufreq/boost ]; then echo 0 > /sys/devices/system/cpu/cpufreq/boost; fi; if [ -w /sys/devices/system/cpu/intel_pstate/no_turbo ]; then echo 1 > /sys/devices/system/cpu/intel_pstate/no_turbo; fi'
   [Install]
   WantedBy=multi-user.target
   ```
   `systemctl daemon-reload && systemctl enable --now qhhoj-judge-tuning.service`.
   **Accepted waiver:** `isolate-check-environment` reports ASLR (`kernel.randomize_va_space=2`) as a problem; the spec (§6) requires ASLR = 2, so that one check is waived. Every other check it reports as `FAIL`, `CAUTION` or `WARNING` (THP and khugepaged defrag, governor, boost, `core_pattern`, swap, SMT) must be fixed; `check-host.sh` enforces exactly this.
2. isolate 2.6: `apt install build-essential libcap-dev libseccomp-dev libsystemd-dev pkg-config git`; `git clone --depth 1 --branch v2.6 https://github.com/ioi/isolate /usr/local/src/isolate && cd /usr/local/src/isolate && make isolate isolate-cg-keeper && make install`; `cp systemd/isolate.service systemd/isolate.slice /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now isolate.service`. In `/usr/local/etc/isolate` keep `box_root = /var/local/lib/isolate` (local disk, never NFS) and `cg_root = auto:/run/isolate/cgroup`. The box count must be at least `box_base + 2 × slots`: with the shipped `subid_user = isolate` it is the smaller of that user's `/etc/subuid` and `/etc/subgid` blocks (`useradd --system isolate` and `usermod --add-subuids 200000-265535 --add-subgids 200000-265535 isolate`), otherwise `num_boxes`. `isolate-check-environment` must be clean except the ASLR check (step 1's waiver). `/usr/local/bin/isolate` must stay `root`-owned and setuid (`4755`).
3. Compilers (the day-one set, legacy-judge-usage.md): `apt install gcc g++ clang fp-compiler python3 pypy3 default-jdk-headless ruby gdc lua5.4 gnat binutils`; Kotlin 2.1.21 from its GitHub release unzipped into `/usr/local/lib` (the judge runs `/usr/local/lib/kotlinc/bin/kotlinc`; judge-v2 `DEPLOY.md` step 3 has the pinned checksum); SCRATCH: `packaging/install-scratch-run.sh` from the judge-v2 release (only if the Scratch conformance gate passed). GAS32 is not offered: isolate 2.6's seccomp filter kills 32-bit binaries.
4. User and directories: `useradd --system --no-create-home --shell /usr/sbin/nologin qhhoj-judge`; `install -d -m 0755 /opt/qhhoj-judge/releases /etc/qhhoj-judge /srv/qhhoj/problem-data`.
5. Problem data over NFS (read-only). On the site host: `apt install nfs-kernel-server`; `/etc/exports`: `/srv/qhhoj/problem-data <judge-ip>(ro,all_squash,anonuid=987,anongid=987,no_subtree_check,sec=sys)` (one line per judge host), `exportfs -ra`; allow TCP 2049 from judge hosts only. On the judge host: `apt install nfs-common`; `/etc/fstab`: `<site-private-ip>:/srv/qhhoj/problem-data /srv/qhhoj/problem-data nfs4 ro,nosuid,nodev,noexec,hard,vers=4.2,actimeo=1,_netdev 0 0`; `mount -a`. `actimeo=1` keeps `.data-version` fresh (the judge waits only 10 s for a newer stamp). `sec=sys` trusts the client's IP and uid: use it only on the private LAN between the site host and judge hosts; a judge outside that LAN needs a WireGuard tunnel (export to its tunnel address) or `sec=krb5p`.
6. TLS (once, on an offline machine or the site host, files kept with the env secrets):
   `openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 3650 -subj "/CN=QHHOJ judge CA" -keyout judge-ca.key -out judge-ca.pem`;
   `openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -subj "/CN=bridge.qhhoj.internal" -keyout bridge.key -out bridge.csr`;
   `openssl x509 -req -in bridge.csr -CA judge-ca.pem -CAkey judge-ca.key -CAcreateserial -days 825 -extfile <(printf "subjectAltName=DNS:bridge.qhhoj.internal,IP:<bridge-private-ip>\nextendedKeyUsage=serverAuth") -out bridge.pem`.
   Site host: `install -d -m 0750 -o root -g 987 /etc/qhhoj/bridge-tls`, `install -m 0644 -o root -g root bridge.pem /etc/qhhoj/bridge-tls/cert.pem` and `install -m 0640 -o root -g 987 bridge.key /etc/qhhoj/bridge-tls/key.pem` (the bridge container runs as uid/gid 987, `deploy/quadlet/qhhoj-bridge.container`); `JUDGE_BRIDGE_TLS_CERT` and `JUDGE_BRIDGE_TLS_KEY` in `/etc/qhhoj/env` point at them (`deploy/env.production.example`). Judge hosts: `install -m 0644 judge-ca.pem /etc/qhhoj-judge/bridge-ca.pem` and resolve `bridge.qhhoj.internal` to the bridge's private address (`/etc/hosts`). `judge-ca.key` never leaves the offline store. Renew the bridge certificate before its 825 days end (same CA, no judge change): install the new pair as above, then `systemctl restart qhhoj-bridge` (the bridge reads the certificate only at boot; judges reconnect and resume their runs within the 30 s grace).
7. Judge key: in the admin UI create the judge; the key is shown once. `install -m 0400 -o root -g root /dev/stdin /etc/qhhoj-judge/key` and paste it. Rotation later: rotate in the UI (the judge is disconnected), replace the file, `systemctl restart qhhoj-judge`.
8. Install the release: `tar -xzf qhhoj-judge-<ver>.tar.gz -C /opt/qhhoj-judge/releases/ && mv /opt/qhhoj-judge/releases/qhhoj-judge-<ver> /opt/qhhoj-judge/releases/<ver>`; `(cd /opt/qhhoj-judge/releases/<ver> && sha256sum -c SHA256SUMS)`; `ln -sfn releases/<ver> /opt/qhhoj-judge/current`. Config: copy `deploy/judge/config.example.toml` to `/etc/qhhoj-judge/config.toml`, set `name` (the admin UI name), `bridge_url = "https://bridge.qhhoj.internal:9990"`, `[tls] server_name`, and leave `slots`/`cores` unset unless the host shares cores. Unit: `cp deploy/judge/qhhoj-judge.service /etc/systemd/system/ && systemctl daemon-reload`; on a host that still runs the old DMOJ judge, do not enable it before the switch (a reboot would start it next to the old judge, both using the isolate boxes): History, Judge switch step 4 (`systemctl enable --now qhhoj-judge`) enables it.
9. Firewall (on a host that still runs the old DMOJ judge: at the switch, History, Judge switch step 3, after saving the old ruleset): `cp deploy/judge/nftables-judge.conf /etc/nftables.conf`, fill the addresses, `nft -c -f /etc/nftables.conf && nft -f /etc/nftables.conf && systemctl enable nftables` (load it explicitly: `enable --now` does not reload a running `nftables.service`), then `nft list chain inet filter output | grep 'policy drop'`. Egress only to the bridge port, NFS (2049) on the site host, DNS, NTP and the apt mirror; ingress only SSH from the admin network.
10. Verify: `sudo -u qhhoj-judge /opt/qhhoj-judge/current/qhhoj-judge selftest --config /etc/qhhoj-judge/config.toml --require "$DAY_ONE_LANGUAGES"` with `DAY_ONE_LANGUAGES=C,C11,CLANG,CPP03,CPP11,CPP14,CPP17,CPP20,CPP23,CLANGX,PY3,PYPY3,PAS,JAVA,JAVA8,KOTLIN,RUBY,D,LUA,ADA,GAS64,TEXT` (judge-v2 CI `JUDGE_SUITE_REQUIRE`; BF is out: Ubuntu 24.04 ships no `bf` interpreter and it had 4 legacy submissions, so it is disabled; append `,SCRATCH` only if the Scratch conformance gate passed) → every line `ok`. Every host runs the same list: `run`'s `prune-languages --keep` (Migration week, `run` step 6) uses this list plus `OUTPUT`, so a language missing on one host is either fixed or dropped from the list on every host before the switch. `deploy/judge/check-host.sh --bridge bridge.qhhoj.internal:9990` → all `ok`; `systemctl show qhhoj-judge -p NoNewPrivileges` must print `NoNewPrivileges=no` (on systemd 255 a `RestrictAddressFamilies=` or similar line must not have implied it; if it prints `yes`, isolate cannot gain its setuid root and every run fails); then (only once the new bridge runs) `systemctl start qhhoj-judge`, `journalctl -u qhhoj-judge -n 20` shows `bridge session started`, the admin judge list shows the judge online with its slots, and an AC submission is graded. `curl -s 127.0.0.1:9464/metrics | grep judge_slots_busy` answers on the host.

## Judge connection

- Judges run judge-v2 (`qhhoj-judge`, repo `judge-v2`) and open a gRPC `qhhoj.judge.v1` link to `JUDGE_BRIDGE_HOST:JUDGE_BRIDGE_PORT` (default 9999; 9990 on the shared host, where the old DMOJ bridge holds 9999), sending the judge name and key as `x-judge-name`/`x-judge-key` metadata. Runs survive a reconnect within 30 s (resume).
- TLS: set `JUDGE_BRIDGE_TLS_CERT` and `JUDGE_BRIDGE_TLS_KEY` (both or neither); a non-loopback host without them refuses to start. Judges pin the private CA (`/etc/qhhoj-judge/bridge-ca.pem`) and check the server name ("Judge hosts" step 6). The pair is read once at start: after renewing it, restart the bridge (`systemctl restart qhhoj-bridge`); judges reconnect and resume. Plaintext is accepted only when the bridge binds loopback (local stacks).
- Create or rotate the judge and its key in the admin UI (the key is shown once; a rotate or block ends every session of the judge and closes its connections at once). Judges are not migrated; register them fresh and issue new keys. On the host the key lives in `/etc/qhhoj-judge/key` (0400 root) and reaches the daemon through `LoadCredential=`; it is re-read on every reconnect.
- Limits: one connection per judge (a newer session replaces the older one); a connection with no session is closed after 15 s; 8 such connections per address; an address with 20 failed key checks in a minute is refused for the rest of that minute (logged as `Judge key check failed from <address>`).
- Only one bridge instance may run. Bind `JUDGE_BRIDGE_HOST` to the private interface and firewall the port to judge hosts; nginx never proxies it. Remote judges connect only over a private network or WireGuard. `/api/internal/openapi.json` is public and lists admin routes (all permission-guarded); deny it in nginx if unwanted.
- Judges need no HTTP access to the site: file-only submissions come over `FetchSource`. Problem data is the read-only NFS mount of `PROBLEM_DATA_ROOT` ("Judge hosts" step 5).
- Update a host: unpack the release into `/opt/qhhoj-judge/releases/<ver>`, `sha256sum -c SHA256SUMS`, `sudo -u qhhoj-judge .../qhhoj-judge selftest --config /etc/qhhoj-judge/config.toml`, `ln -sfn releases/<ver> /opt/qhhoj-judge/current`, `systemctl restart qhhoj-judge` (SIGTERM drains: no new work, running submissions finish for up to 120 s). Roll hosts one at a time, waiting for each to show online. Roll back a release by pointing `current` at the previous one and restarting.
- Local development: `STACK_JUDGE=none npm run stack:up && npm run judge:v2:up` (CONTRIBUTING "Local judge").

7. Freeze of the old site: `supervisorctl stop` its programs (site, celery, celerybeat, bridged, wsevent) and `docker stop pcd` (the DMOJ judge). Other supervisor programs and containers stay running.

8. Hosts: v2 serves only `qhhoj.com` (API at `https://qhhoj.com/api/`). The pre-cutover `v2.qhhoj.com` demo and `api-v2.qhhoj.com` API-only hosts were removed in 2026-10 (nginx blocks, certificates and DNS records).

### Judge switch

Per judge machine, against the review stack (`qhhoj.target` running, bridge on 9990). The shared host's old judge is the container `pcd`, already stopped at the freeze; the judge-v2 machine is separate and has no old judge, so steps 1 and 2 apply only to a host that still runs a DMOJ judge.

1. Old-DMOJ hosts only: save the running firewall for the rollback: `install -d -m 0700 /root/qhhoj-rollback && nft list ruleset > /root/qhhoj-rollback/ruleset.nft && { systemctl is-enabled nftables > /root/qhhoj-rollback/nftables-enabled 2>&1 || true; }`; it must exit 0, else stop: the Cutover rollback needs the saved ruleset (also note any other firewall unit, e.g. `systemctl is-active ufw`).
2. Old-DMOJ hosts only: `systemctl disable --now <old DMOJ judge unit>`.
3. Install and load the judge firewall ("Judge hosts" step 9; `nft -f` loads it even when `nftables.service` was already running), and check it is the live one: `nft list chain inet filter output | grep -q 'policy drop' && nft list chain inet filter output | grep -q 'dport { 2049, 9990 }' && echo firewall-ok` (if the bridge listens on another port, grep for that port instead of 9990).
4. `systemctl enable --now qhhoj-judge`; `journalctl -u qhhoj-judge -n 20` shows `bridge session started` and the admin judge list shows the host online with its slots.
5. Re-check the host: `deploy/judge/check-host.sh --bridge bridge.qhhoj.internal:9990` → every line `ok`, the egress check included (it was the one expected FAIL before the switch).
6. Submit one AC, one WA and one CE on a known problem through the site and see the verdicts arrive live.

### Cutover rollback

The rollback target was the old site with its DMOJ judge; there was no mixed state (new site with DMOJ judges, or old site with judge-v2).

- Before go-live (no write has reached v2): `systemctl stop qhhoj.target`, restore the backed-up nginx file (`cp -a /root/qhhoj-rollback/nginx-default /etc/nginx/sites-enabled/default && nginx -t && systemctl reload nginx`), `supervisorctl start` the old programs (site, celery, celerybeat, bridged, wsevent), `docker start pcd`. Nothing was lost. Judge machine: `systemctl disable --now qhhoj-judge` first. A host that ran the old DMOJ judge before: restore the firewall saved in Judge switch step 1 (`nft flush ruleset && nft -f /root/qhhoj-rollback/ruleset.nft`; an empty saved file leaves no rules); if `/root/qhhoj-rollback/nftables-enabled` does not say `enabled`, `systemctl disable --now nftables`, else put the saved ruleset back as `/etc/nftables.conf`; re-enable any other firewall unit that was active; check `nft list ruleset | grep -c 'policy drop'` against `grep -c 'policy drop' /root/qhhoj-rollback/ruleset.nft`; then `systemctl enable --now <old DMOJ judge unit>`. Confirm the DMOJ judge shows online in the old site's judge list before reopening it.
- After go-live: new-site writes exist only in Mongo. Decide quickly: either accept the loss and do the steps above (the old database is frozen, so it misses everything since the freeze), or fix forward. There is no reverse migration; submissions made on the new site are not replayed to the old one. On a different host the DNS switches back as well.
- Keep the old database, uploads, supervisor programs, the `pcd` container and the nginx backup unmodified until the rollback period (suggest 2 weeks, and at least one clean week of judge-v2) ends; then remove the old judge.
