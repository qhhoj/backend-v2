# Production runbook

Files: `nginx/qhhoj.conf`, `nginx/security-headers.conf`, `nginx/qhhoj-gate.conf`, `quadlet/*`, `qhhoj-deploy`, `ci/*`, `migrate/qhhoj-migrate`, `env.production.example`, `judge/*`.
Layout: image `ghcr.io/qhhoj/backend-v2` run by rootful podman quadlets (`/etc/containers/systemd/`, host network, uid/gid 987); frontend under `/var/www/qhhoj/releases/<version>` with `current`; data `/srv/qhhoj`; env `/etc/qhhoj/env`; nginx, MongoDB and Redis native.
This host is the shared live old-site box (`160.22.123.77`), v2 goes in place; judge-v2 runs on a separate machine. Never stop, restart or reconfigure anything on it that is not QHHOJ's.

## Prerequisites

- podman >= 4.9 (Ubuntu 24.04 package; installed beside Docker, host network only), nginx >= 1.25.1 (older: `listen 443 ssl http2;`), MongoDB 8 as a replica set `rs0` with auth, Redis >= 7, `mongosh`, `mongodb-database-tools`, `rsync`, `openssl`, `mariadb-client` (for `qhhoj-migrate snapshot`). The worker toolchain (Node, pandoc, Chromium) is in the image; about 2 GB per PDF job plus 2 GiB for similarity.
- Disk: `MEDIA_ROOT`, `PROBLEM_DATA_ROOT`, `PDF_CACHE_ROOT`, `CONTEST_DATA_ROOT`, `USER_DATA_ROOT` as separate directories under `/srv/qhhoj` owned by uid/gid 987 (none under `MEDIA_ROOT`). At least 20 GiB free there (`qhhoj-migrate run` refuses less).
- TLS certificate for the site host; firewall: 80/443 public; `PORT` (3000) closed to everything but loopback (the api also binds 127.0.0.1 via `LISTEN_HOST`); `JUDGE_BRIDGE_PORT` from judge hosts only.
- Read access to the legacy MariaDB and its Django `SECRET_KEY`.

## In-place on the shared host

One-time steps, already performed on `160.22.123.77`; repeat them on a rebuild.

1. Minecraft server stopped for good (2026-10-10): graceful `stop` in its `screen` session `minecraft-apio`; it had no autostart; files kept in `/root/minecraft-apio`. Also disabled as unused on this VM: `qhhoj.service` (the old failed `/root/start_qhhoj.sh`), ModemManager, udisks2, upower, multipathd, open-iscsi, thermald, gpu-manager, open-vm-tools, vgauth.
2. podman 4.9.3 from the Ubuntu 24.04 packages, next to Docker. v2 containers use `--network host` only; Docker and its apps are untouched.
3. MongoDB 8.0.32 (`mongodb-org`) from the mongodb.org noble repo. `/etc/mongod.conf`: `replSetName: rs0`, `bindIp: 127.0.0.1`, `storage.wiredTiger.engineConfig.cacheSizeGB: 2`, `keyFile: /etc/mongod.keyfile`, `authorization: enabled`. Users `admin` (root) and `qhhoj` (`readWrite` + `dbAdmin` on `qhhoj`, `clusterMonitor`); passwords in `/root/qhhoj-secrets/mongo.env` (mode 600), never in this repo.
4. Redis is the host's existing one (6379). The old site uses db0/db1; v2 uses `REDIS_URL=redis://127.0.0.1:6379/4`.
5. Judge bridge: `JUDGE_BRIDGE_PORT=9990` (the old DMOJ bridge holds 9999). `ufw allow from <judge-machine-ip> to any port 9990 proto tcp`; no other rule opens it. The judge machine's `config.toml` `bridge_url` and `nftables-judge.conf` `BRIDGE_PORT` use 9990 too.
6. nginx: the old `qhhoj.com` server block lives in `/etc/nginx/sites-enabled/default` next to other domains' blocks. At the freeze (Migration week, day 1) back the file up (`cp -a /etc/nginx/sites-enabled/default /root/qhhoj-rollback/nginx-default`) and replace only that block with `deploy/nginx/qhhoj.conf` (the existing qhhoj.com certificate paths); leave every other block untouched; `nginx -t && systemctl reload nginx`. Cloudflare stays in front, so go-live needs no DNS change.
7. Freeze of the old site (Migration week, day 1): `supervisorctl stop` its programs (site, celery, celerybeat, bridged, wsevent) and `docker stop pcd` (the DMOJ judge). Other supervisor programs and containers stay running.

## First install

1. Install the packages above (this host: see "In-place on the shared host").
2. Copy `deploy/` to the host (`scp -r deploy root@host:/root/qhhoj-deploy`) and run `bash /root/qhhoj-deploy/install-host.sh`. It is idempotent: creates the users `qhhoj` (uid/gid 987) and `deploy`, the directories (`/srv/qhhoj/*`, `/etc/qhhoj`, `/var/lib/qhhoj-deploy`), and installs the helper scripts, quadlets and sudoers; it never starts services. It refuses if uid/gid 987 is taken by another account (then rebuild the image with `--build-arg QHHOJ_UID=<free id>` and change `ID` in the script). Let nginx read the data group: `usermod -aG qhhoj www-data` (`nginx` on nginx.org packages), then restart nginx; the units' `UMask=0027` keeps new files group-readable and setgid keeps the group, nginx reads `/media/` through that group (without it every `/media/` request is 403). Judges sharing `PROBLEM_DATA_ROOT` need the same group or a read mount. For legacy rsync use `--chown=987:987 --chmod=D2750,F640`.
3. `/etc/qhhoj/env` from `env.production.example` (mode 600; unquoted `KEY=value`, podman `--env-file` format); `ENCRYPTION_KEY`, `TOKEN_SECRET` by `openssl rand -hex 32`; `MONGO_URL` with the `qhhoj` user from `/root/qhhoj-secrets/mongo.env`; on the shared host `REDIS_URL=redis://127.0.0.1:6379/4`, `JUDGE_BRIDGE_PORT=9990`. Bridge TLS: `chown root:987 /etc/qhhoj/bridge-tls/key.pem && chmod 640` it ("Judge hosts" step 6 makes the pair).
4. GHCR: CD logs in per deploy with the workflow's `GITHUB_TOKEN` (`qhhoj-deploy backend <tag> --token-stdin`), no token on the host. For a manual `qhhoj-deploy backend <tag>` without it: `podman login ghcr.io --authfile /etc/qhhoj/ghcr-auth.json` with a classic token limited to `read:packages` (fine-grained tokens cannot read GHCR), then `chmod 600` it.
5. nginx: `deploy/nginx/qhhoj.conf` to `conf.d/` (on the shared host: the in-place block replacement above) with the `CHANGE` lines, `security-headers.conf` to `snippets/qhhoj-security-headers.conf`, `qhhoj-gate.conf` to `snippets/qhhoj-gate.conf`, `maintenance.html` to `/var/www/qhhoj-maintenance/` (`install-host.sh` does these three); `nginx -t && systemctl reload nginx`. TLS: reuse the site certificate (copy it from the old host if the host is new until DNS points here), then `certbot` on this host.
6. CD access: `ssh-keygen -t ed25519 -N '' -f /root/deploy_key`, append the public key to `/var/lib/qhhoj-deploy/.ssh/authorized_keys` (owner `deploy`, mode 600); in both GitHub repos create environment `production` with secrets `DEPLOY_HOST`, `DEPLOY_SSH_KEY` (the private key; then delete it from the host), `DEPLOY_KNOWN_HOSTS` (`ssh-keyscan <host>`).
7. First deploy: run the backend and frontend `deploy` workflows by hand (empty ref); `qhhoj-deploy status` shows both. A backend deploy (re)starts `qhhoj.target`, before the migration too: it then runs against the empty database, which is harmless (nginx still serves the old site; `qhhoj-migrate run` stops it).
8. Indexes are built by the migration (`run` syncs them); on an empty database run `syncIndexes` before serving (the `.hint()` queries throw without them).

## Migration week

Freeze-and-iterate: the old site is frozen once (up to a week down), its dump is loaded into a throwaway MariaDB container, and `qhhoj-migrate run` rebuilds Mongo from it as often as needed until staff approve. `go-live` is the single irreversible step. Everything runs on the v2 host as root with `qhhoj-migrate` (installed by `install-host.sh`); logs in `/var/log/qhhoj-migrate/<stamp>/` (`summary.txt`, per-step logs, `timings.tsv`); work dir `/srv/qhhoj-migrate` (`incoming/` holds the dump, `media/`, `problem-data/`).

`qhhoj-migrate` commands:

- `snapshot`: frozen read-only copy of the local old site into `incoming/`: `mysqldump --single-transaction` (root socket auth) to `legacy-<UTC stamp>.sql.gz` plus rsync of `LEGACY_MEDIA_DIR` (default `/qhh/media`) and `LEGACY_PROBLEM_DIR` (default `/qhh/problems`); prints the dump path. `LEGACY_DB_NAME` defaults to `qhhoj`. On a host that is not the old site, copy the dump, media and problem data into `incoming/` by hand instead.
- `import-dump <file.sql.gz>`: loads the dump into a temporary MariaDB container (`qhhoj-legacy`, 127.0.0.1:3307) and writes `LEGACY_MYSQL_URL` for the migrator. Replaces the previous import; refused after go-live.
- `run [--accept-rating-coverage]`: every step in order, repeatable: stops `qhhoj.target`, `audit`, `backfill --fresh`, `grant-permissions`, reserved problem codes check, `verify`, `recompute` (starts the worker alone), file sync from `incoming/`, `check-files`, `check-integrity`, `stamp-data-versions`, `count-data-shapes`, `prune-languages` (dry run, then real). The first failing step stops the run (log path printed). `--accept-rating-coverage` accepts a check-integrity failure only when every line is a rating-coverage line (see the ruling below) and records it in `summary.txt`. It refuses without a loaded dump, below 20 GiB free, with a missing or non-600 env file, or with `MIGRATION_REHEARSAL` set; it waits for a running deploy (`qhhoj-deploy` lock).
- `preview on` / `preview off`: maintenance gate (writes `/etc/nginx/snippets/qhhoj-gate.conf`, mode 600): every visitor gets `/maintenance.html` ("We'll be back soon", 503 with `Retry-After`) from `/var/www/qhhoj-maintenance`; staff open the printed link `https://<site>/__preview?key=<token>` once (14-day cookie) and reach the site; loopback is exempt for health checks. The token is shown once; `preview on` again issues a new one. `go-live` turns it off.
- `go-live`: asks for the typed word `go-live`; stops the stack, `finish` (clears the migration marker, marks the site live), `mongodump` to `/backup/qhhoj-cutover.gz`, starts `qhhoj.target`, gate off, smoke check. Resumable if a later step fails. After it `run` and `import-dump` refuse: never backfill after finish.
- `status`: went-live flag, the snapshot hash, the last good run's summary.

`/root/migrate.env` (mode 600; `qhhoj-migrate` reads it, delete it after the rollback period):

| Variable                                                   | Needed by                                                                                      |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `MONGO_URL`                                                | every command                                                                                  |
| `LEGACY_MYSQL_URL`                                         | audit, backfill, verify, check-integrity (not set by hand: `import-dump` writes `legacy.env`)  |
| `LEGACY_SECRET_KEY`, `ENCRYPTION_KEY`                      | backfill and verify (users job: decrypts legacy 2FA secrets, re-seals them); required by `run` |
| `MEDIA_URL` (default `/media`)                             | backfill and verify (problems, sources), check-files                                           |
| `REDIS_URL`                                                | recompute (same Redis and Mongo as the worker)                                                 |
| `DAY_ONE_LANGUAGES`                                        | `run`'s prune-languages keep list (below); required                                            |
| `LEGACY_DB_NAME`, `LEGACY_MEDIA_DIR`, `LEGACY_PROBLEM_DIR` | `snapshot` (optional, defaults above)                                                          |

`MONGO_URL`, `REDIS_URL`, `MEDIA_URL` and `ENCRYPTION_KEY` must equal the values in `/etc/qhhoj/env` (`run` refuses otherwise). A different `ENCRYPTION_KEY` seals every migrated TOTP secret and scratch code under a key the api does not hold, and `verify` cannot see it: every 2FA user would be locked out. The file roots are fixed by the command (`/srv/qhhoj/media`, `/srv/qhhoj/problem-data`).

The week, in order:

1. Before the freeze (days ahead): judge machine provisioned and verified ("Judge hosts", steps 1-8 and 10; the firewall of step 9 can go in at once, the machine has no old judge); the judge-v2 release unpacked and `selftest` clean; the parity run (`scripts/judge/parity/README.md`) without unclassified differences on this release; a dry run on a current dump (`qhhoj-migrate snapshot` or a copied dump, `import-dump`, `run`) with its timings kept; `count-data-shapes` exits 0 in it (a Pascal or Java bridged checker needs a testlib judge-v2 does not ship: convert it to C++ first). Announce the downtime; lower the DNS TTL if DNS will change.
2. Day 1, freeze: back up the nginx file, replace the qhhoj.com block, `supervisorctl stop` the old site programs and `docker stop pcd` ("In-place on the shared host", steps 6-7); the old site now serves nothing, new submissions stop. (On a host that is not the old site: old nginx rejects POST/PUT/PATCH/DELETE with a 503 notice, workers and judge intake stopped, in-flight submissions finished.) Then `qhhoj-migrate snapshot` and `qhhoj-migrate import-dump <printed path>`.
3. `qhhoj-migrate run`. Read `qhhoj-migrate status` and the logs; a `check-integrity` rating-coverage shortfall is judged by the ruling below and, if accepted, re-run once with `--accept-rating-coverage`. Work through the manual items. `run` is not interactive and cannot damage the snapshot: re-run freely.
4. Review: `systemctl start qhhoj.target`, `qhhoj-migrate preview on`; staff open the printed preview link (the public sees the maintenance page); run the smoke checks except judging. Findings: fix, release (CD), `systemctl stop qhhoj.target`, `qhhoj-migrate run` again (a fresh run replaces the whole database). Same for a newer dump: `snapshot`/`import-dump`/`run`. A migrator fix changes only the image; nothing needs the old site.
5. Switch the judges, one machine at a time, against the review stack ("Judge switch" below). Judge hosts reach the bridge through the firewall opening for 9990; the review gate does not touch the bridge.
6. On the user's explicit go: `echo go-live | qhhoj-migrate go-live` (it stops the stack itself). After it the old data is never re-imported.
7. DNS: none on the shared host (same address behind Cloudflare). On a different host switch DNS now; all sessions are invalidated once, users log in again.
8. Watch `journalctl -u 'qhhoj-*' -f`, the judge list and `curl -s 127.0.0.1:9464/metrics` on each judge (`judge_assignments_total`, `judge_sandbox_failures_total`, `judge_reconnects_total`) for 30 minutes. Keep the old site, its database and `pcd` untouched for the rollback period. HSTS ships at `max-age=300` for that period; afterwards raise it to `31536000` in `nginx/security-headers.conf`. The SPA CSP ships as Report-Only: after a few clean days rename it to `Content-Security-Policy`.

### What `run` does (step reference)

`run` performs steps 1-6 below, in this order, in a container of the current image; each is a migrator command (`APP=migrator`, same env) if it must be run by hand when debugging. Steps 7-8 are `go-live`.

1. `audit` (read-only). Read its warnings; the manual items below come from it. Time it too: its zero-date scan reads every date column, including the 13M-row activity table.
2. `backfill --fresh --report <path>`: empties each selected collection and upserts by `_id` (ids stay stable through `migrationIdMap`; rows deleted on the old site disappear). It writes the migration marker the worker requires. Every report line (ids, codes and keys only, no row data) is saved to the run's `backfill-report.txt` (mode 600); the manual items below are read from it. Never run `backfill` against the live database after `finish`: it re-arms the marker and with it the rating wipe.
   2a. `grant-permissions`: gives each v2-only permission to the groups and users holding its anchor (`judge.change_contest_tag` <- `judge.edit_all_contest`, `judge.delete_problem` <- `judge.edit_all_problem`, `judge.manage_short_link` <- `flatpages.change_flatpage`, `judge.manage_integration` <- `judge.change_miscconfig`; groups and users holding the anchor directly both get the codename; the full list is `apps/migrator/src/permission-grants.ts`) (idempotent, rerun after every `backfill --fresh`, which rewrites `groups` from the legacy rows). `verify` ignores the codenames it adds.
   2b. Reserved problem codes: `db.problems.countDocuments({ code: { $in: ['deleted', 'meta', 'imports'] } })` must be 0; a problem with such a code is already shadowed by the static routes and must be renamed on the old site first.
3. `verify` must exit 0; exit 1 lists mismatches (job and document).
4. `recompute`: starts only the worker (`qhhoj-worker`; the api and bridge stay stopped) and runs the worker's `migration-recompute` job (points, stats, scores, caches; re-rates every rated contest, see decisions.md), then stops it. It needs a running worker on the same Redis and Mongo (detected with Redis `CLIENT LIST`; a managed Redis that forbids it needs a self-hosted one) and is retried while the worker boots. Allow hours (6 h timeout).
5. File sync and checks: `rsync --delete` of `incoming/media` and `incoming/problem-data` into `/srv/qhhoj` (media includes `submission_file/`). Audit the media tree: `find /srv/qhhoj/media -type f ! -path '*/submission_file/*' | sed 's/.*\.//' | sort | uniq -c`; nginx serves only png/jpg/jpeg/gif/webp/svg/pdf/txt inline and everything else as a download. `check-files` (exit 1 lists missing files, first 50 shown) and `check-integrity` (references, counts, rating coverage; exit 1 on a problem) must exit 0, except as ruled below. `check-files` also warns about `pdfStatementUrl`/`materialUrl` site paths outside `MEDIA_URL` (they cannot be checked here): open each by hand on the new host.

   Rating coverage ("legacy-rated participations without a v2 rating", "v2 ratings without a legacy rating", "rated contests: legacy N, v2 M") can differ legitimately because the replay re-rates (users cross the rating floor and ceiling; contests legacy marked rated but never rated get rows). Any other line (references, "submissions scoring above their problem's points", stale user ratings) is still an abort. For a rating shortfall: read the per-contest breakdown; a handful of contests with few missing rows is accepted (`--accept-rating-coverage`) and recorded in the decisions log; a shortfall spread over many contests, or any contest missing most of its rows, means the replay did not run: abort, re-run, and check the worker log.

6. Stamp, shapes, languages (after the file sync: an `rsync --delete` from the legacy tree removes stamps):
   - `stamp-data-versions --root /srv/qhhoj/problem-data`. The summary must show `invalidCode: 0`; `missingDirectory` counts problems without data on disk (they were IE on the old site too); `symlinked` lists problems whose data directory is or holds a symlink, which judge-v2 refuses (IE): it must be empty, else replace those links by copies in the legacy tree. Re-running is safe.
   - `count-data-shapes` (see week step 1).
   - `prune-languages --keep "$DAY_ONE_LANGUAGES,OUTPUT"` (dry run, then real), before the judges switch (a submission in a language no judge advertises would sit in QU forever). Set the list literally in `/root/migrate.env`, the exact list every judge host's `selftest --require` passed ("Judge hosts" step 10; `OUTPUT` needs no runtime):
     ```sh
     DAY_ONE_LANGUAGES=C,C11,CLANG,CPP03,CPP11,CPP14,CPP17,CPP20,CPP23,CLANGX,PY3,PYPY3,PAS,JAVA,JAVA8,KOTLIN,RUBY,D,LUA,ADA,BF,GAS64,TEXT
     ```
     The command refuses (exit 1, nothing written) a list with no runtime language (an unset variable) and any key that names no language. Compare `prunedLanguages` and `problemsChanged` of the dry run with the rehearsal's, and keep `prunedLanguages`, `problemsChanged`, `languagesDisabled` and `emptiedProblems` (in `summary.txt`) in the notes; announce them to problem setters. GAS32 and the other pruned languages keep their rows (disabled), so old submissions still show their language. A language added to the fleet later is re-allowed per problem by its editors.
7. `finish` (in `go-live`): clears the migration marker, so the worker refuses `migration-recompute` from then on. Never after the site takes writes (`went-live` enforces it).
8. `mongodump` of the migrated database to `/backup/qhhoj-cutover.gz` (in `go-live`) before the services start.

For a rehearsal without the legacy `SECRET_KEY`, the standalone migrator (not `qhhoj-migrate run`, which forbids it) may run `backfill` and `verify` with `--skip-legacy-secrets` under `MIGRATION_REHEARSAL=1` (refused otherwise): no `LEGACY_SECRET_KEY` or `ENCRYPTION_KEY`, the canary is skipped, every user migrates with 2FA off. The real migration must never set `MIGRATION_REHEARSAL` or pass that flag: it would lock 2FA off for every account. The migrator needs about `NODE_OPTIONS=--max-old-space-size=3072` inside a 4 GB limit (`run` sets both). Data dirs and the MariaDB/Mongo datadirs of a rehearsal must not be under `/tmp` (size-limited tmpfs; a 4.5 GB import fills it, "table is full"); `import-dump` keeps its datadir under `/srv/qhhoj-migrate/mariadb`. Drop `migrationIdMap` once if a rehearsal ran older migrator code (`db.migrationIdMap.drop()`); production starts empty.

Manual items:

- Deactivated superusers. Old-site admin-deactivated accounts migrate banned ("Account deactivated on the old site.", inactive, unlisted). Staff cannot unban a superuser in the UI. The audit warning "auth_user deactivated superusers" gives the count. Leave them banned: they could not log in on the old site either. Re-enable one only on an explicit decision that the person regains access (`db.users.updateOne({ username: "<name>" }, { $set: { isActive: true, banReason: null, isUnlisted: false } })` restores full superuser access, a grant the old site did not give). To let staff manage the account instead, demote it: `$set: { isSuperuser: false, isStaff: false }`.
- Lua label scripts: 6 contests use one; v2 has only numeric and alpha labels, so they become alpha and the report says `judge_contest:<id> Lua label script -> alpha`. Staff open each of the 6 and check the problem labels.
- Clamped points: 19 problems had points outside 800..3500 and were clamped (`clamped points judge_problem:<id> <old> -> <new>` in the report). The submissions job rescored those problems' graded submissions against the clamped points, so their user points and stats stay consistent. Review the new points with the problem setters; if one changes, a `problem-rescore` fixes its submissions.
- RJ test cases: case status `RJ` is not a v2 status; those cases are dropped and counted in the report (submission totals are unaffected).
- Judges are not migrated (names fail the v2 pattern and judge-v2 registers fresh): create judges and keys in the admin UI after go-live.
- Canary skip: the users job checks `LEGACY_SECRET_KEY` against the first `totp_key`, else the first `scratch_codes`. With neither it logs "no legacy secret to test LEGACY_SECRET_KEY against (canary skipped)": check the key by hand then. A wrong key aborts the users job.
- Not migrated, tell the users: API tokens (`judge_profile.api_token`; regenerate them) and IP auth.
- Template-valued misc config entries are kept raw and only reported: convert them by hand. Re-enter the legacy site settings (the env/settings import is paused) in the admin UI.
- Permissions that exist only in v2 (for example `judge.change_settings`, `judge.import_polygon_package`, `judge.create_mass_testcases`) are held by no migrated group, except those `grant-permissions` derives from an anchor permission (see `apps/migrator/src/permission-grants.ts`, e.g. `judge.change_contest_tag`, `judge.delete_problem`). Superusers bypass them; grant them to the staff groups that need them.
- Badges, legacy ratings, activity, sessions and logs are not migrated by decision; users log in again.

### Judge switch

Per judge machine, against the review stack (`qhhoj.target` running, bridge on 9990). The shared host's old judge is the container `pcd`, already stopped at the freeze; the judge-v2 machine is separate and has no old judge, so steps 1 and 2 apply only to a host that still runs a DMOJ judge.

1. Old-DMOJ hosts only: save the running firewall for the rollback: `install -d -m 0700 /root/qhhoj-rollback && nft list ruleset > /root/qhhoj-rollback/ruleset.nft && { systemctl is-enabled nftables > /root/qhhoj-rollback/nftables-enabled 2>&1 || true; }`; it must exit 0, else stop: Rollback step 2 needs the saved ruleset (also note any other firewall unit, e.g. `systemctl is-active ufw`).
2. Old-DMOJ hosts only: `systemctl disable --now <old DMOJ judge unit>`.
3. Install and load the judge firewall ("Judge hosts" step 9; `nft -f` loads it even when `nftables.service` was already running), and check it is the live one: `nft list chain inet filter output | grep -q 'policy drop' && nft list chain inet filter output | grep -q 'dport { 2049, 9990 }' && echo firewall-ok` (if the bridge listens on another port, grep for that port instead of 9990).
4. `systemctl enable --now qhhoj-judge`; `journalctl -u qhhoj-judge -n 20` shows `bridge session started` and the admin judge list shows the host online with its slots.
5. Re-check the host: `deploy/judge/check-host.sh --bridge bridge.qhhoj.internal:9990` → every line `ok`, the egress check included (it was the one expected FAIL before the switch).
6. Submit one AC, one WA and one CE on a known problem through the site and see the verdicts arrive live; if `count-data-shapes` listed `nestedCaseNames`, also submit an AC on one of those problems.

## Smoke checks

- `curl -fsS https://HOST/api/internal/site` returns JSON; `curl -I https://HOST/some/spa/route` returns 200 with the HTML shell.
- `curl -N https://HOST/api/internal/events/...` as a logged-in user prints a heartbeat within 15 s without delay (proves unbuffered).
- Log in, open a problem, submit a solution; a judge grades it; the verdict appears live (in the review only once a judge is switched, Judge switch step 6).
- A statement PDF renders (worker + Chromium + pandoc); an uploaded image shows from `/media/`.
- `ss -ltn | grep 9990` is open locally but unreachable from outside the judge machine (ufw); `systemctl status qhhoj-*` all active.
- `curl -sI https://HOST/s/nonexistent` is 404 (not the SPA shell: proves the `/s/` location); an integration key from outside its `allowedCidrs` is refused on `/api/sync/v1/...`.
- Registration works only after `mail.smtpUrl` is set (admin settings, `judge.change_settings`).

## Integration clients (sync API)

- `TRUST_PROXY` must be set behind nginx: each client's CIDR check and the failed-key lockout (20 bad `qhi_` keys in 10 minutes from one address answer 429 for every key from it) use `request.ip`; without it all clients share the proxy's address (the api logs a boot warning when active clients exist).
- After `grant-permissions`, check at rehearsal that a migrated admin group holds `judge.manage_integration` (its anchor is `judge.change_miscconfig`); superusers bypass it.
- A client's acting user must not be a superuser and must hold `judge.add_contest` and `judge.create_private_contest`; it may hold more than the key's creator, so use a dedicated account. Keys may carry `expiresAt`; each client gets 60 requests per minute.
- nginx needs the `/s/` and `/api/sync/` locations from `deploy/nginx/qhhoj.conf`.

## Deploy notes

- Stream caps per api process (fixed defaults, no env override): public submission feed 900 (was 1000), contest event-feed streams 100 (`contestFeedTotal`, new), contest streams 1500, notification streams 2000, total 5000. The caps add up to 4500, which leaves 500 slots for submission and ticket streams. Beyond a cap the api answers 429; with several api processes behind nginx each process counts on its own. A load balancer or monitoring that assumed 1000 feed streams per process needs the new numbers.
- CD: a release tag builds the image, pushes it to GHCR and deploys after CI passes (SSH as `deploy`, `sudo qhhoj-deploy`); Actions -> deploy -> Run workflow deploys any ref (`force` for a running contest). Exit 75 = deferred (a contest is running, or a migration holds the lock): retry later; `qhhoj-deploy backend <tag> [--force]`, `qhhoj-deploy frontend <version>`, `qhhoj-deploy rollback backend|frontend` (previous history entry), `qhhoj-deploy status` (live versions and history). A failed health check rolls back by itself. During the migration week deploy a migrator fix as usual; `qhhoj-migrate run` and `go-live` wait for a running deploy. The helper scripts themselves (`qhhoj-deploy`, `qhhoj-migrate`, quadlets, sudoers) update only by re-running `install-host.sh` from a fresh copy of `deploy/`.
- Request bodies over a route's limit answer 413 with error code `payload_too_large` (it was `http_error`).

## Backup

- Secrets: keep `/etc/qhhoj/env` (at least `ENCRYPTION_KEY`, `TOKEN_SECRET`) in an offline secret store, separate from the dumps; encrypted settings and 2FA secrets in a dump are useless without the same `ENCRYPTION_KEY`.
- Mongo: `mongodump --uri "$MONGO_URL" --gzip --archive=/backup/qhhoj-$(date +%F).gz` nightly (no `--oplog`: not point-in-time, acceptable nightly); restore with `mongorestore --gzip --archive=... --drop`. Test a restore once.
- Data roots: restic (or dated snapshots, not a `--delete` mirror) of `MEDIA_ROOT` and `PROBLEM_DATA_ROOT` nightly, right after the mongodump; `PDF_CACHE_ROOT`, `CONTEST_DATA_ROOT` and `USER_DATA_ROOT` are regenerable and need no backup.
- Redis holds no durable state (queue truth is Mongo); no backup needed.

## Rollback

The rollback target is the old site with its DMOJ judge; there is no mixed state (new site with DMOJ judges, or old site with judge-v2).

- Deploy level (any time): `qhhoj-deploy rollback backend` or `rollback frontend`; `qhhoj-deploy status` shows the live versions. Releases are re-tagged images, so this is seconds.
- Before go-live (no write has reached v2): `systemctl stop qhhoj.target`, restore the backed-up nginx file (`cp -a /root/qhhoj-rollback/nginx-default /etc/nginx/sites-enabled/default && nginx -t && systemctl reload nginx`), `supervisorctl start` the old programs (site, celery, celerybeat, bridged, wsevent), `docker start pcd`. Nothing was lost. Judge machine: `systemctl disable --now qhhoj-judge` first. A host that ran the old DMOJ judge before: restore the firewall saved in Judge switch step 1 (`nft flush ruleset && nft -f /root/qhhoj-rollback/ruleset.nft`; an empty saved file leaves no rules); if `/root/qhhoj-rollback/nftables-enabled` does not say `enabled`, `systemctl disable --now nftables`, else put the saved ruleset back as `/etc/nftables.conf`; re-enable any other firewall unit that was active; check `nft list ruleset | grep -c 'policy drop'` against `grep -c 'policy drop' /root/qhhoj-rollback/ruleset.nft`; then `systemctl enable --now <old DMOJ judge unit>`. Confirm the DMOJ judge shows online in the old site's judge list before reopening it.
- After go-live: new-site writes exist only in Mongo. Decide quickly: either accept the loss and do the steps above (the old database is frozen, so it misses everything since the freeze), or fix forward. There is no reverse migration; submissions made on the new site are not replayed to the old one. On a different host the DNS switches back as well.
- A bad judge-v2 release alone is not a site rollback: point `/opt/qhhoj-judge/current` at the previous release and restart (Judge connection).
- Keep the old database, uploads, supervisor programs, the `pcd` container and the nginx backup unmodified until the rollback period (suggest 2 weeks, and at least one clean week of judge-v2) ends; then remove the old judge.

## Judge hosts

Dedicated Ubuntu 24.04 hosts, nothing else on them. Per host, as root:

1. Kernel and boot: cgroups v2 is the default on 24.04 (`/sys/fs/cgroup/cgroup.controllers` exists). Turn SMT off (`echo off > /sys/devices/system/cpu/smt/control` and `nosmt` in `GRUB_CMDLINE_LINUX`, `update-grub`), swap off (`swapoff -a`, remove the swap line from `/etc/fstab`), `sysctl -w kernel.randomize_va_space=2`, `kernel.apparmor_restrict_unprivileged_userns=1` and `kernel.core_pattern=core` (persist all three in `/etc/sysctl.d/90-qhhoj-judge.conf`), `apt install unattended-upgrades chrony linux-tools-common linux-tools-$(uname -r)`. Timing stability, persisted by a oneshot unit:
   ```ini
   # /etc/systemd/system/qhhoj-judge-tuning.service
   [Unit]
   Description=Judge host CPU and memory tuning (THP off, performance governor, boost off)
   Before=qhhoj-judge.service isolate.service
   [Service]
   Type=oneshot
   RemainAfterExit=yes
   ExecStart=/bin/sh -c 'echo never > /sys/kernel/mm/transparent_hugepage/enabled; echo never > /sys/kernel/mm/transparent_hugepage/defrag; echo 0 > /sys/kernel/mm/transparent_hugepage/khugepaged/defrag'
   ExecStart=/usr/bin/cpupower frequency-set -g performance
   ExecStart=/bin/sh -c 'if [ -w /sys/devices/system/cpu/cpufreq/boost ]; then echo 0 > /sys/devices/system/cpu/cpufreq/boost; fi; if [ -w /sys/devices/system/cpu/intel_pstate/no_turbo ]; then echo 1 > /sys/devices/system/cpu/intel_pstate/no_turbo; fi'
   [Install]
   WantedBy=multi-user.target
   ```
   `systemctl daemon-reload && systemctl enable --now qhhoj-judge-tuning.service`.
   **Accepted waiver:** `isolate-check-environment` reports ASLR (`kernel.randomize_va_space=2`) as a problem; the spec (§6) requires ASLR = 2, so that one check is waived. Every other check it reports as `FAIL`, `CAUTION` or `WARNING` (THP and khugepaged defrag, governor, boost, `core_pattern`, swap, SMT) must be fixed; `check-host.sh` enforces exactly this.
2. isolate 2.6: `apt install build-essential libcap-dev libsystemd-dev pkg-config git`; `git clone --depth 1 --branch v2.6 https://github.com/ioi/isolate /usr/local/src/isolate && cd /usr/local/src/isolate && make isolate isolate-cg-keeper && make install`; `cp systemd/isolate.service systemd/isolate.slice /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now isolate.service`. In `/usr/local/etc/isolate` keep `box_root = /var/local/lib/isolate` (local disk, never NFS) and `cg_root = auto:/run/isolate/cgroup`. The box count must be at least `box_base + 2 × slots`: with the shipped `subid_user = isolate` it is the smaller of that user's `/etc/subuid` and `/etc/subgid` blocks (`useradd --system isolate` and `usermod --add-subuids 200000-265535 --add-subgids 200000-265535 isolate`), otherwise `num_boxes`. `isolate-check-environment` must be clean except the ASLR check (step 1's waiver). `/usr/local/bin/isolate` must stay `root`-owned and setuid (`4755`).
3. Compilers (the day-one set, legacy-judge-usage.md): `apt install gcc g++ clang fp-compiler python3 pypy3 default-jdk-headless ruby gdc lua5.4 gnat bf binutils`; Kotlin from its GitHub release into `/opt/kotlinc` with `/usr/bin/kotlinc` linked to it; SCRATCH: `packaging/install-scratch-run.sh` from the judge-v2 release (only if plan B Task 35's gate passed). GAS32 is not offered: isolate 2.6's seccomp filter kills 32-bit binaries.
4. User and directories: `useradd --system --no-create-home --shell /usr/sbin/nologin qhhoj-judge`; `install -d -m 0755 /opt/qhhoj-judge/releases /etc/qhhoj-judge /srv/qhhoj/problem-data`.
5. Problem data over NFS (read-only). On the site host: `apt install nfs-kernel-server`; `/etc/exports`: `/srv/qhhoj/problem-data <judge-ip>(ro,all_squash,anonuid=987,anongid=987,no_subtree_check,sec=sys)` (one line per judge host), `exportfs -ra`; allow TCP 2049 from judge hosts only. On the judge host: `apt install nfs-common`; `/etc/fstab`: `<site-private-ip>:/srv/qhhoj/problem-data /srv/qhhoj/problem-data nfs4 ro,nosuid,nodev,noexec,hard,vers=4.2,actimeo=1,_netdev 0 0`; `mount -a`. `actimeo=1` keeps `.data-version` fresh (the judge waits only 10 s for a newer stamp). `sec=sys` trusts the client's IP and uid: use it only on the private LAN between the site host and judge hosts; a judge outside that LAN needs a WireGuard tunnel (export to its tunnel address) or `sec=krb5p`.
6. TLS (once, on an offline machine or the site host, files kept with the env secrets):
   `openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -days 3650 -subj "/CN=QHHOJ judge CA" -keyout judge-ca.key -out judge-ca.pem`;
   `openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -subj "/CN=bridge.qhhoj.internal" -keyout bridge.key -out bridge.csr`;
   `openssl x509 -req -in bridge.csr -CA judge-ca.pem -CAkey judge-ca.key -CAcreateserial -days 825 -extfile <(printf "subjectAltName=DNS:bridge.qhhoj.internal,IP:<bridge-private-ip>\nextendedKeyUsage=serverAuth") -out bridge.pem`.
   Site host: `install -d -m 0750 -o root -g 987 /etc/qhhoj/bridge-tls`, `install -m 0644 -o root -g root bridge.pem /etc/qhhoj/bridge-tls/cert.pem` and `install -m 0640 -o root -g 987 bridge.key /etc/qhhoj/bridge-tls/key.pem` (the bridge container runs as uid/gid 987, `deploy/quadlet/qhhoj-bridge.container`); `JUDGE_BRIDGE_TLS_CERT` and `JUDGE_BRIDGE_TLS_KEY` in `/etc/qhhoj/env` point at them (`deploy/env.production.example`). Judge hosts: `install -m 0644 judge-ca.pem /etc/qhhoj-judge/bridge-ca.pem` and resolve `bridge.qhhoj.internal` to the bridge's private address (`/etc/hosts`). `judge-ca.key` never leaves the offline store. Renew the bridge certificate before its 825 days end (same CA, no judge change): install the new pair as above, then `systemctl restart qhhoj-bridge` (the bridge reads the certificate only at boot; judges reconnect and resume their runs within the 30 s grace).
7. Judge key: in the admin UI create the judge; the key is shown once. `install -m 0400 -o root -g root /dev/stdin /etc/qhhoj-judge/key` and paste it. Rotation later: rotate in the UI (the judge is disconnected), replace the file, `systemctl restart qhhoj-judge`.

Config: copy `deploy/judge/config.example.toml` to `/etc/qhhoj-judge/config.toml`, set `name` (the admin UI name), `bridge_url = "https://bridge.qhhoj.internal:9990"`, `[tls] server_name`, and leave `slots`/`cores` unset unless the host shares cores. Unit: `cp deploy/judge/qhhoj-judge.service /etc/systemd/system/ && systemctl daemon-reload`; on a host that still runs the old DMOJ judge, do not enable it before the switch (a reboot would start it next to the old judge, both using the isolate boxes): Judge switch step 4 enables it.

Firewall (on a host that still runs the old DMOJ judge: at the switch, Judge switch step 3, after saving the old ruleset): `cp deploy/judge/nftables-judge.conf /etc/nftables.conf`, fill the addresses, `nft -c -f /etc/nftables.conf && nft -f /etc/nftables.conf && systemctl enable nftables` (load it explicitly: `enable --now` does not reload a running `nftables.service`), then `nft list chain inet filter output | grep 'policy drop'`. ## Judge connection

- Judges run judge-v2 (`qhhoj-judge`, repo `judge-v2`) and open a gRPC `qhhoj.judge.v1` link to `JUDGE_BRIDGE_HOST:JUDGE_BRIDGE_PORT` (default 9999; 9990 on the shared host, where the old DMOJ bridge holds 9999), sending the judge name and key as `x-judge-name`/`x-judge-key` metadata. Runs survive a reconnect within 30 s (resume).
- TLS: set `JUDGE_BRIDGE_TLS_CERT` and `JUDGE_BRIDGE_TLS_KEY` (both or neither); a non-loopback host without them refuses to start. Judges pin the private CA (`/etc/qhhoj-judge/bridge-ca.pem`) and check the server name ("Judge hosts" step 6). The pair is read once at start: after renewing it, restart the bridge (`systemctl restart qhhoj-bridge`); judges reconnect and resume. Plaintext is accepted only when the bridge binds loopback (local stacks).
- Create or rotate the judge and its key in the admin UI (the key is shown once; a rotate or block ends every session of the judge and closes its connections at once). Judges are not migrated; register them fresh and issue new keys. On the host the key lives in `/etc/qhhoj-judge/key` (0400 root) and reaches the daemon through `LoadCredential=`; it is re-read on every reconnect.
- Limits: one connection per judge (a newer session replaces the older one); a connection with no session is closed after 15 s; 8 such connections per address; an address with 20 failed key checks in a minute is refused for the rest of that minute (logged as `Judge key check failed from <address>`).
- Only one bridge instance may run. Bind `JUDGE_BRIDGE_HOST` to the private interface and firewall the port to judge hosts; nginx never proxies it. Remote judges connect only over a private network or WireGuard. `/api/internal/openapi.json` is public and lists admin routes (all permission-guarded); deny it in nginx if unwanted.
- Judges need no HTTP access to the site: file-only submissions come over `FetchSource`. Problem data is the read-only NFS mount of `PROBLEM_DATA_ROOT` ("Judge hosts" step 5).
- Update a host: unpack the release into `/opt/qhhoj-judge/releases/<ver>`, `sha256sum -c SHA256SUMS`, `sudo -u qhhoj-judge .../qhhoj-judge selftest --config /etc/qhhoj-judge/config.toml`, `ln -sfn releases/<ver> /opt/qhhoj-judge/current`, `systemctl restart qhhoj-judge` (SIGTERM drains: no new work, running submissions finish for up to 120 s). Roll hosts one at a time, waiting for each to show online. Roll back a release by pointing `current` at the previous one and restarting.
- Local development: `STACK_JUDGE=none npm run stack:up && npm run judge:v2:up` (CONTRIBUTING "Local judge").
